# Happy path: сценарии для ручной проверки

Сценарии независимы: каждый начинается с чистого состояния (свежая вкладка или
явный повторный вход).

## Подготовка

```bash
docker compose up --build   # из корня репозитория
```

Поднимутся: `postgres` (5432), `redis` (6379), `backend` (8000, Swagger —
`http://localhost:8000/docs`), `worker`, `frontend` (`http://localhost:5173`).
Без ключей `AI_LLM__PROVIDER=fake`: конвейер проходит целиком, но черновик
приходит с пометкой «оценить вручную». Сценарии проверяют, что путь работает, а
не что модель дала хороший ответ.

Четыре сеяных аккаунта, один пароль (`avito2026`): `student`, `reviewer`,
`methodist`, `admin`. Переключатель в шапке сам логинится в нужный аккаунт. Плюс
аккаунт на каждую карточку из `backend/reviewers/` — логин совпадает с именем
файла (`c-bahtin`, `c-eremina`, …).

С ключом модели вердикты становятся содержательными:

```bash
AI_LLM__PROVIDER=external AI_LLM__API_KEY="$ключ" docker compose up -d backend worker
```

**Особенность docker-compose:** nginx во `frontend`-контейнере резолвит имя
`backend` один раз при своём старте. После пересборки одного бэкенда
(`docker compose up --build -d backend`) запросы к `/api/*` начнут отвечать
`502`. Лечится `docker compose restart frontend`.

## 1. Вход и видимость по ролям

Проверяет RBAC на уровне интерфейса и бэкенда: не только разные кнопки, но и
разные токены под ними.

1. Откройте `http://localhost:5173/rubrics` в приватном окне. Экран должен
   открыться под ролью «ревьюер» и показать каталог рубрик.
2. Кнопки «Собрать из условия» быть не должно — рубрики собирает только
   руководитель.
3. Переключите роль на «Руководитель». Кнопка должна появиться; во вкладке
   Network должен быть новый `POST /auth/login` с `username: "admin"`.
4. В Swagger `POST /auth/login` с `{"username": "coordinator", "password":
   "avito2026"}` — ожидаемо `401`: роли «координатор» в бэкенде нет.
5. Нажмите «Войти» и войдите под `student`/`avito2026` — ожидаемая ошибка «у
   роли student пока нет экрана в этом интерфейсе»: форма отклоняет её сама.
   Заведите второго ревьюера (сценарий 7) и войдите под ним — шапка должна
   показать его `display_name` и роль «ревьюер».

## 2. Разбор сдачи по ссылке

Проверяет `/check` → ingest → gate → ревью → (опционально) детектор →
`/review/:id` целиком по-настоящему.

1. Под ролью «ревьюер» откройте `/check`.
2. Ссылка — любой публичный PR. Готовый вариант без токена:
   `https://github.com/psf/requests/pull/6951`. Анонимный лимит GitHub — 60
   запросов в час на весь контейнер; 502 с упоминанием `INGEST_GITHUB__TOKEN`
   означает исчерпанный лимит.
3. Рубрика — любая из списка. Дедлайн и id студента не обязательны.
4. Отметьте «Проверить на признаки ГенИИ» и запустите разбор. На `fake` —
   секунды; на настоящем ключе — минуты (наблюдалось 4 минуты), и это не
   зависание: `frontend/nginx.conf` держит таймаут прокси на 300s под это.
5. Должно перекинуть на `/review/<id>`: файлы слева, черновик по критериям,
   отчёт детектора. Плашки «демо-прогон» быть не должно.
6. Откройте `/queue` — сдача в списке со статусом `черновик готов` и баллом.
   Клик открывает ту же карточку, но уже через `GET /submissions/{id}`
   (проверяется открытием ссылки в новой вкладке).

## 3. Правки ревьюера

Проверяет, что правка балла и вердикта детектора уходят на сервер и переживают
перезагрузку страницы. Продолжение сценария 2.

1. У любого критерия поправьте балл кнопками ± и нажмите «Готово». Строка
   показывает «Балл поправлен ревьюером», итог наверху обновляется.
2. **Перезагрузите страницу.** Поправленный балл должен остаться.
3. Если есть спан ГенИИ — подтвердите или отклоните его. Балл не должен
   измениться: вердикт детектора рекомендательный.
4. «Утвердить». Повторное утверждение (`POST /submissions/{id}/review/approve`)
   — `409`.
5. В Swagger под токеном `reviewer` вызовите
   `POST /submissions/{id}/ai-detection/{span_id}/verdict` на **уже
   утверждённой** сдаче. Ожидаемо не `409`, а `200` (или `404` на случайный id):
   подтверждение спана не блокируется утверждением.

## 4. Чат ревьюера с моделью

Проверяет, что SSE-эндпоинт `/submissions/{id}/chat` стримит с бэкенда через
nginx-прокси. Продолжение сценария 2 или 3.

1. В нижней части `/review/:id` разверните «Разговор с моделью».
2. Задайте вопрос («Обоснуй балл по первому критерию»). Пока ответ считается,
   поле ввода недоступно; ответ приходит одним блоком, без перезагрузки.
3. Перезагрузите страницу — вопрос и ответ должны быть на месте: история
   читается с сервера (`GET .../chat`).
4. Если модель предложила конкретную правку, у сообщения появится кнопка
   «Применить». Балл по критерию обновляется как при ручной правке, кнопка
   меняется на «Применено». (На `fake`-провайдере ожидаемо «Модель не ответила».)
5. На демо-прогоне (`/review/demo`) чат содержит записанную переписку, поле
   ввода заблокировано: PATCH'ить нечего — сдачи не существует.

## 5. Сборка и подтверждение рубрики

Проверяет путь методиста: условие задания превращается в критерии.

1. Под ролью «Руководитель» откройте `/rubrics` → «Собрать из условия».
2. Заполните id задания (`e2e-check`) и вставьте условие текстом — подойдёт пара
   предложений с конкретными требованиями («реализуйте GET /ping, верните 200»).
3. «Собрать рубрику». На `fake` ожидаемо «0 критериев, открытые вопросы» — это
   видимый отказ вместо выдуманных цифр. С настоящим ключом появляются критерии
   с пометкой «дословная цитата / пересказ / источник не найден».
4. Подтвердите черновик. Рубрика появляется в каталоге и в `/check`.
5. Уберите её: `DELETE /rubrics/{assignment_id}` под токеном `admin`. Повторный
   `GET /rubrics/{id}` — `404`, из `/check` она пропадает.

## 6. Переназначение и повтор проверки

Проверяет, что очередь Redis/arq забирает задачу и пересчитывает черновик без
повторного похода за PR.

1. Под токеном `admin`: `POST /submissions/{id}/reassign` с
   `{"reviewer_username": "reviewer"}` на сдаче из сценария 2.
2. `GET /me/queue?all=true` — `reviewer_id` сменился.
3. `POST /submissions/{id}/review/rerun` → `202`, статус переходит в `analyzing`.
4. `docker compose logs worker --tail 20` — строка о задаче `rerun_review`.
   `GET /submissions/{id}` — статус вернулся в `draft_ready` (или `error`, если
   модель недоступна, но не завис в `analyzing`).
5. `docker compose stop redis`, повторите `rerun` — ожидаемо `503`, не зависшая
   ручка и не 500. Верните redis.

## 7. Управление аккаунтами

Проверяет `/users` как CRUD. Экрана во фронте нет: заводить и менять роли — через
Swagger, входить под заведённым аккаунтом — через кнопку «Войти».

1. Под токеном `admin`: `POST /users` — `{"username": "reviewer-2", "password":
   "s3cret123", "role": "reviewer", "display_name": "Второй ревьюер"}` → `201`.
2. Во фронте «Войти» под `reviewer-2`/`s3cret123` — шапка показывает «Второй
   ревьюер», роль «ревьюер».
3. `PATCH /users/{id}` — смените ему роль на `admin`; `GET /users` показывает
   двоих `admin`.
4. Удалите **исходного** `admin` — должно пройти (`204`). Затем попробуйте
   удалить последнего оставшегося — ожидаемо `409`: сидинг заполняет только
   пустую таблицу `users`, и рестарт контейнера роль не вернёт.
5. Удалите `reviewer`, за которым числится сдача из сценария 2 — ожидаемо `409`;
   переназначьте (сценарий 6) и повторите — `204`.

## 8. Экономика и аудит

1. `/check` показывает блок «Экономика прогона» внизу страницы. После сценария 2
   счётчик обращений и сумма должны вырасти.
2. Под токеном `admin`: `GET /audit/llm-calls` — построчный журнал, каждая
   запись с хостом эндпоинта.

## 9. Учебный контур: задание, сдача, раскладка

Проверяет то, ради чего заведены курсы и потоки: срок задаёт методист, студент
сдаёт сам, работы раздаёт руководитель.

1. **Методист** (`/assignments`) — «Новое задание»: поток, рубрика, срок. У
   задания без даты написано «срока нет», а не прочерк.
2. **Ревьюер** (`/check`) — в форме **выбор задания**, а не поле дедлайна: срок
   принадлежит заданию. Под селектором — число критериев, максимум и срок.
3. **Руководитель** (`/streams`) — развернуть поток, «Назначить» ревьюеров. У
   ревьюера с карточкой в `backend/reviewers/` подтянутся его минуты и навыки; у
   сеяного `reviewer` будет написано, что карточки нет.
4. **Студент** (`/my-work`) — «Сдать работу», ссылка на pull request. После сдачи
   у работы **нет балла** — «на проверке у ревьюера». Это главное, что проверяет
   сценарий.
5. **Руководитель** — «Разложить работы»: число «без ревьюера» на плитке
   становится нулём.
6. **Ревьюер** (`/queue`) — работа в очереди, разбор открывается, «Утвердить».
7. **Студент** — виден балл, разбор по критериям и отзыв словами.

Что должно быть **не** так: студент не видит чужих работ (404), не открывает
`/submissions/{id}` с цитатами (403), не читает статистику потока (403).

## 10. Разбор на настоящих сдачах

В репозитории лежат учебные pull request'ы с решениями студентов — по одному на
задание, против пустой ветки `demo/base` (состав — в [demo-data.md](demo-data.md)).
Вставьте ссылку в «Проверить работу» с заданием по Go.

Что стоит увидеть:

- **работа проходит целиком даже с непройденным требованием**: строка «Не
  выполнено требование условия: …» стоит над разбором, а разбор сделан;
- **цитаты кликабельны** — переход подсвечивает нужные строки слева;
- **отзыв о работе** идёт первым блоком, критерии следом, объяснение итога
  последним; над списком закреплена ровно одна строка;
- **вкладка «Признаки ГенИИ»** делит окно с черновиком.

У всех этих PR сигнал ГенИИ равен `0.40`: форензика даёт 0.80 каждой, потому что
каждая ветка собрана одним коммитом. Правило срабатывает на способ сборки демо, а
не на работу студента — подробности в [demo-data.md](demo-data.md).
