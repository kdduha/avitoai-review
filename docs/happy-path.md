# Happy path: сценарии для ручной проверки

Документ для того, кто хочет своими руками наклацать интерфейс и убедиться,
что каждый путь действительно работает — не по коду, а по экрану. Сценарии
независимы: каждый начинается с чистого состояния (свежая вкладка или явный
повторный вход) и его можно прогнать отдельно от остальных.

## Подготовка

```bash
docker compose up --build   # из корня репозитория
```

Поднимутся: `postgres` (5432), `redis` (6379), `backend` (8000, Swagger —
`http://localhost:8000/docs`), `worker`, `frontend` (`http://localhost:5173`).
Без ключей `AI_LLM__PROVIDER=fake` — конвейер проходит целиком, но черновик
приходит с пометкой «оценить вручную» вместо содержательного вердикта. Это
нормально и ожидаемо: сценарии ниже проверяют, что путь работает, а не что
конкретная модель дала хороший ответ.

Четыре сеяных аккаунта, один пароль (`avito2026`): `student`, `reviewer`,
`methodist`, `admin`. Переключатель в шапке сам логинится в нужный
бэкенд-аккаунт; во фронте роли называются так же, как на сервере. Плюс аккаунт
на каждую карточку из `backend/reviewers/` — логин совпадает с именем файла
(`c-bahtin`, `c-eremina`, …), пароль тот же.

С ключом модели вместо `fake` сценарии дают содержательные вердикты:

```bash
AI_LLM__PROVIDER=external AI_LLM__API_KEY="$ключ" docker compose up -d backend worker
```

**Известная особенность docker-compose**: если пересобрать и перезапустить
только `backend` (`docker compose up --build -d backend`), фронтенд не
заметит — nginx во `frontend`-контейнере резолвит имя `backend` один раз при
своём старте и держит старый IP. После пересборки одного бэкенда без фронта
запросы с `/api/*` начнут отвечать `502 Bad Gateway`. Лечится
`docker compose restart frontend`.

## 1. Вход и видимость по ролям

Проверяет: RBAC на уровне интерфейса и бэкенда — не только разные кнопки, но
и разные токены под ними.

1. Откройте `http://localhost:5173/rubrics` в приватном окне (свежий
   `localStorage`). Экран должен открыться под ролью «ревьюер» и показать
   каталог рубрик — если каталог не загрузился, бэкенд недоступен раньше, чем
   вы успели проверить остальное.
2. Кнопки «Собрать из условия» на экране быть не должно — рубрики собирает
   только руководитель.
3. Переключите роль в шапке на «Руководитель». Кнопка «Собрать из условия»
   должна появиться. Откройте вкладку браузера Network — переключение роли
   должно было отправить новый `POST /auth/login` с `username: "admin"`.
4. Откройте `http://localhost:8000/docs`, `POST /auth/login` с телом
   `{"username": "coordinator", "password": "avito2026"}` — ожидаемый ответ
   `401`: роль «координатор» в бэкенде больше не существует, ревьюер и
   руководитель — это `reviewer` и `admin`.
5. Нажмите «Войти» в шапке и войдите под сеяным `student`/`avito2026` —
   ожидаемая ошибка «у роли student пока нет экрана в этом интерфейсе»: форма
   отклоняет её сама, до попытки что-либо показать. Заведите второго ревьюера
   (сценарий 7) и войдите под ним тем же окном — шапка должна показать его
   `display_name` и логин, роль — «ревьюер».

## 2. Разбор сдачи по ссылке

Проверяет: `/check` → ingest → gate → ревью → (опционально) детектор →
`/review/:id`, целиком по-настоящему, не по записанному прогону.

1. Под ролью «ревьюер» откройте `/check`.
2. Ссылка — любой публичный PR на GitHub. Готовый вариант без токена:
   `https://github.com/psf/requests/pull/6951` (репозиторий на ~130 файлов,
   не упирается в порог инлайна). Анонимный лимит GitHub — 60 запросов в час
   на весь контейнер; если сценарий 502-ит с упоминанием `INGEST_GITHUB__TOKEN`
   — лимит исчерпан, подождите час или добавьте токен в `.env`.
3. Рубрика — любая из выпадающего списка. Дедлайн и внутренний id студента не
   обязательны для happy path.
4. Отметьте «Проверить на признаки ГенИИ» и нажмите «Запустить разбор».
   На `fake`-провайдере — секунды. На настоящем ключе разбор с несколькими
   критериями и детектором может занимать минуты (реально наблюдалось — 4
   минуты на одном прогоне) — это не зависание, страница просто ждёт ответ;
   `frontend/nginx.conf` держит таймаут прокси на 300s именно под это.
5. Вас должно перекинуть на `/review/<id>`. На экране: панель с файлами
   слева, черновик по критериям в центре, отчёт детектора справа. Плашки
   «демо-прогон» быть не должно — это живой разбор.
6. Откройте `/queue` — только что созданная сдача должна быть в списке, с
   правильным статусом (`черновик готов`) и баллом. Кликните по ней — должна
   открыться та же карточка, но уже через `GET /submissions/{id}`, а не из
   памяти вкладки (проверить это можно, открыв ссылку на сдачу в новой
   вкладке — предыдущая ничего туда не передавала).

## 3. Правки ревьюера

Проверяет: правка балла и вердикта детектора уходят на сервер и переживают
перезагрузку страницы — не остаются локальной прикидкой.

Продолжение сценария 2 (нужен `submission_id` живого прогона).

1. У любого критерия нажмите на балл, поправьте его кнопками ±, нажмите
   «Готово». Строка должна показать «Балл поправлен ревьюером», а итог наверху
   — обновиться.
2. **Перезагрузите страницу браузера.** Поправленный балл должен остаться —
   если он вернулся к исходному значению, правка ушла только в память
   вкладки, а не на сервер.
3. Если разбор запускался с признаками ГенИИ и в правой панели есть хотя бы
   один спан — подтвердите или отклоните его. Балл при этом не должен
   измениться: вердикт детектора рекомендательный.
4. Нажмите «Утвердить». Повторное нажатие (или утверждение той же сдачи ещё
   раз через Swagger, `POST /submissions/{id}/review/approve`) должно вернуть
   `409` — сдача уже утверждена.
5. В Swagger, под токеном `reviewer`, вызовите
   `POST /submissions/{id}/ai-detection/{любой-span-id}/verdict` на **уже
   утверждённой** сдаче. Ожидаемо — не `409`, а нормальная обработка (`200`
   на существующий спан или `404` на случайный id): подтверждение спана не
   должно блокироваться утверждением, это разные вещи.

## 4. Чат ревьюера с моделью

Проверяет: SSE-эндпоинт `/submissions/{id}/chat` реально стримит с бэкенда
через nginx-прокси фронтенда, а не показывает заглушку.

Продолжение сценария 2 или 3 (нужна живая, ещё не обязательно утверждённая
сдача).

1. В нижней части `/review/:id` разверните «Разговор с моделью».
2. Задайте вопрос — например, «Обоснуй балл по первому критерию» — и
   отправьте. Пока ответ считается, поле ввода должно быть недоступно; ответ
   приходит одним блоком (это не токен-стриминг — сервер досчитывает весь ход
   и только потом отдаёт его), но без перезагрузки страницы.
3. Перезагрузите страницу и разверните чат снова — тот же вопрос и ответ
   должны быть на месте: история читается с сервера (`GET .../chat`), а не
   хранится в компоненте.
4. Если рубрика и модель дают содержательный ответ (не «Модель не ответила» —
   это ожидаемо на `fake`-провайдере без ключа, см. §7 ниже), а модель
   предложила конкретную правку, у сообщения появится кнопка «Применить».
   Нажмите её — балл по указанному критерию должен обновиться так же, как
   при ручной правке из сценария 3, а кнопка — смениться на «Применено».
5. На демо-прогоне (`/review/demo`, без бэкенда за ним) разверните тот же
   чат — там должна быть заранее записанная переписка и поле ввода
   заблокировано с плейсхолдером «Демо-ветка: ответы записаны заранее»:
   бэкенду в принципе нечего PATCH'ить для сдачи, которой не существует.

## 5. Сборка и подтверждение рубрики

Проверяет: путь методиста — условие задания превращается в критерии, а не
вводится вручную.

1. Под ролью «Руководитель» откройте `/rubrics`, нажмите «Собрать из
   условия».
2. Заполните id задания (например, `e2e-check`) и вставьте условие текстом —
   подойдёт пара предложений с конкретными требованиями («реализуйте GET
   /ping, верните 200»).
3. Нажмите «Собрать рубрику». На `fake`-провайдере ожидаемо честное «0
   критериев, открытые вопросы» — это не баг, а видимый отказ вместо
   выдуманных цифр (см. `docs/handover-backend.md`, «Почему матрица, а не одна модель»). С
   настоящим ключом должны появиться критерии с пометкой у каждого —
   дословная цитата / пересказ / источник не найден.
4. Подтвердите черновик. Рубрика должна появиться в каталоге `/rubrics` и
   быть выбираемой в `/check`.
5. Уберите её: в Swagger, под токеном `admin`,
   `DELETE /rubrics/{assignment_id}`. Повторный `GET /rubrics/{id}` —
   `404`; в `/check` она пропадает из выпадающего списка.

## 6. Переназначение и повтор проверки

Проверяет: очередь Redis/arq реально забирает задачу и пересчитывает черновик
без повторного похода за PR.

1. В Swagger под токеном `admin`: `POST /submissions/{id}/reassign` с
   `{"reviewer_username": "reviewer"}` (или заведите второго ревьюера — см.
   §7) на сдаче из сценария 2.
2. `GET /me/queue?all=true` — `reviewer_id` у сдачи должен смениться.
3. `POST /submissions/{id}/review/rerun`. Ответ — `202`, статус сдачи
   переходит в `analyzing`.
4. `docker compose logs worker --tail 20` — должна появиться строка о
   выполненной задаче `rerun_review`. `GET /submissions/{id}` — статус должен
   вернуться в `draft_ready` (или `error`, если модель недоступна, но не
   зависнуть в `analyzing`).
5. Остановите `redis` (`docker compose stop redis`) и повторите `rerun` —
   ожидаемый ответ `503`, а не зависшая ручка или 500. Верните `redis`
   обратно (`docker compose start redis`).

## 7. Управление аккаунтами

Проверяет: `/users` — рабочий CRUD, а не единственный способ завести второго
ревьюера — это правка базы руками. Экрана управления аккаунтами во фронте
пока нет (см. `docs/handover-frontend.md`), заводить и менять роли — только
через Swagger; входить под заведённым аккаунтом — уже можно через кнопку
«Войти» в шапке.

1. Под токеном `admin`: `POST /users` —
   `{"username": "reviewer-2", "password": "s3cret123", "role": "reviewer", "display_name": "Второй ревьюер"}`.
   Ответ — `201`.
2. Во фронте нажмите «Войти», введите `reviewer-2`/`s3cret123` — шапка должна
   показать «Второй ревьюер» и роль «ревьюер». (Или напрямую `POST
   /auth/login` под новым логином — токен с ролью `reviewer`.)
3. `PATCH /users/{id}` — смените ему роль на `admin`, затем `GET /users` —
   в списке должно быть двое `admin`.
4. Попробуйте удалить **исходного** `admin` (`DELETE /users/{id}` с id
   сеяного аккаунта) — раз второй admin уже есть, должно пройти (`204`).
   Затем попробуйте удалить последнего оставшегося admin — ожидаемо `409`:
   без него некому будет зайти под этой ролью, и восстановить её рестартом
   контейнера нельзя — сидинг заполняет только пустую таблицу `users`.
5. Попробуйте удалить `reviewer`, за которым числится сдача из сценария 2
   (`DELETE /users/{id}`) — ожидаемо `409` с объяснением переназначить сдачи
   сначала; переназначьте (сценарий 6) и повторите — теперь `204`.

## 8. Экономика и аудит

Проверяет: журнал шлюза действительно считает вызовы, а не показывает нули
статикой.

1. `/check` показывает блок «Экономика прогона» внизу страницы (виден и без
   запуска разбора). После сценария 2 обновите страницу — счётчик обращений
   и потраченная сумма должны вырасти.
2. В Swagger, под токеном `admin`: `GET /audit/llm-calls` — построчный журнал,
   каждая запись с хостом эндпоинта (не одинаковые записи на внешний и
   локальный вызов).

---

Если какой-то сценарий не воспроизводится — прежде чем считать это багом,
проверьте: не исчерпан ли анонимный лимит GitHub (сценарий 2), не забыт ли
`docker compose restart frontend` после пересборки одного бэкенда (см.
«Подготовка»), и не относится ли путь к синтетике (`/queue`, `/courses/*`,
`/curators` пока не читают реальный бэкенд — см. `docs/handover-frontend.md`).

## 9. Учебный контур: задание, сдача, раскладка

Проверяет то, ради чего заведены курсы и потоки: срок задаёт методист, студент
сдаёт сам, работы раздаёт руководитель.

1. **Методист** (`/assignments`) — «Новое задание»: выбрать поток, рубрику,
   поставить срок. Задание появляется в списке со сроком словами; у задания без
   даты написано «срока нет», а не прочерк — это разные вещи.
2. Открыть `/check` **ревьюером**. В форме должен быть **выбор задания**, а не
   поле дедлайна: срок принадлежит заданию. Под селектором — число критериев,
   максимум и срок из задания.
3. **Руководитель** (`/streams`) — развернуть поток, «Назначить» ревьюеров.
   У ревьюера с карточкой в `backend/reviewers/` подтянутся его настоящие
   минуты и навыки; у сеяного `reviewer` будет написано, что карточки нет.
4. **Студент** (`/my-work`) — задания сгруппированы по курсам. «Сдать работу»,
   вставить ссылку на pull request. После сдачи у работы **нет балла** —
   «на проверке у ревьюера». Это главное, что проверяет сценарий.
5. **Руководитель** — «Разложить работы»: сдачи без ревьюера получают
   исполнителя, и число «без ревьюера» на плитке становится нулём.
6. **Ревьюер** (`/queue`) — работа появилась в очереди, разбор открывается,
   «Утвердить оценку».
7. **Студент** — теперь виден балл, разбор по критериям и отзыв словами.

Что должно быть **не** так: студент не видит чужих работ (404), не открывает
`/submissions/{id}` с цитатами (403) и не читает статистику потока (403).

## 10. Разбор на настоящих сдачах

В репозитории лежат учебные pull request'ы с решениями студентов — по одному на
задание, против пустой ветки `demo/base`. Вставьте ссылку в «Проверить работу»
с заданием по Go.

Что стоит увидеть:

- **работа проходит целиком даже с непройденным требованием.** Гейт сообщает,
  но не запрещает: строка «Не выполнено требование условия: …» стоит над
  разбором, а разбор при этом сделан;
- **цитаты кликабельны** — переход подсвечивает нужные строки в панели работы;
- **отзыв о работе** идёт первым блоком, критерии — следом, объяснение итога —
  последним; над списком закреплена ровно одна строка;
- **вкладка «Признаки ГенИИ»** делит окно с черновиком, переключается вручную.

Известная особенность этих PR: у всех сигнал ГенИИ равен `0.40`, потому что
форензика истории даёт 0.80 каждой — **каждая ветка собрана одним коммитом**.
Правило «вся работа одним коммитом» срабатывает честно, но говорит про способ
сборки демо-веток, а не про студента: организаторы опубликовали снимок
репозитория без истории. Стилометрия и модель-судья при этом работают и дают
разные спаны по разным работам.
