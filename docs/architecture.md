# Avito AI Reviewer — архитектура решения

**Кейс:** AI-помощник ревьюера и координатора образовательных программ Авито (хакатон AITH / TalentHub).
**Формат решения:** веб-платформа-админка для кураторов и ревьюеров.
**Горизонт:** хакатон-MVP за 24–48 часов, но с архитектурой, которая масштабируется на другие курсы и каналы сдачи.

---

## 0. TL;DR для питча

Мы делаем **не бота, а рабочее место ревьюера**: одна вкладка вместо GitHub + Google Docs + Sheets.

Четыре опоры решения:

1. **Канонизация сдачи.** На входе стоит абстракция `ProviderInput`: она принимает ссылку (на PR, документ, страницу курса) и конвертирует её в единый объект `SubmissionBundle`. В первой итерации реализован один `ProviderInput` — GitHub; Google Docs и Stepik подключаются как новые реализации того же интерфейса, остальная система не меняется. Всё, что выше по стеку, про источник не знает — это и есть масштабируемость на другие курсы.
2. **Дешёвое перед дорогим.** Сначала классификатор артефактов и Format Gate — детерминированные проверки, которые не стоят ни одного токена и закрывают то, что ревьюер делает руками в первую минуту. Модель запускается только на том, что прошло гейт.
3. **Grounded-ревью с обязательными цитатами.** LLM не ставит оценку. LLM выдаёт по каждому критерию вердикт + **обязательную цитату** (файл, строки / фрагмент документа). Итоговый балл считает детерминированный агрегатор в коде. Ревьюер видит, откуда взялся каждый вывод, и может кликнуть на цитату.
4. **Приватный контур.** Единственная точка выхода к внешним LLM — `PrivacyGateway`. Прямые вызовы провайдеров запрещены архитектурно и ловятся в CI. Всё, что содержит ПДн, либо обезличивается, либо уходит только на локальную модель.

Разделение труда между кодом и моделью — сквозной принцип: **модель понимает содержание, код принимает решения.** Модель разбирает работу, строит профиль сложности и объясняет; баллы, распределение, штрафы и формальные проверки считает детерминированный код.

Human-in-the-loop не декларация, а механика: ревьюер **утверждает / правит / итеративно уточняет** черновик в чате с моделью, и любая правка пишется в `review_revisions` с указанием авторства (ai / human / ai-assisted).

## 1. Что мы автоматизируем (и что осознанно не трогаем)

| Этап текущего процесса | Сейчас | В решении |
|---|---|---|
| Публикация задания и критериев | Методист вручную | Импорт задания + рубрики в систему (одноразово на курс) |
| Формирование ведомости, распределение | Google Sheets, вручную | **Auto-assignment** по нагрузке/капасити/дедлайнам |
| Сдача работы | PR / ссылка на Docs | **Webhook + polling**, автозахват работы |
| Проверка формата (объём, шрифт, число тест-кейсов) | Глазами, первым делом | **Format Gate** — детерминированно, до запуска модели |
| Первичное ревью | 30 мин руками | **AI-черновик** по критериям с цитатами → ревьюер за 10–15 мин |
| Проверка на ГенИИ | Не делается системно | **Отдельный агент-детектор** + git/revision-форензика, спаны в UI |
| Обратная связь студенту | Пишется руками | Черновик в нужном ToV, ревьюер правит |
| Фиксация результата | Ручной перенос в Sheets | **Автозапись** в Sheets + запись в БД |
| Контроль сроков | Ручной пинг | **Дашборд просрочек** у координатора (без внешних уведомлений) |
| **Итоговая оценка и спорные случаи** | Ревьюер | **Ревьюер** (не автоматизируем — ограничение ТЗ) |

## 2. Контекст: акторы и внешние системы

```
                 ┌───────────────────────────────────────────────┐
   Студент ──PR──▶        Avito AI Reviewer (наша платформа)      │
                 │                                               │
   Ревьюер ──────▶  веб-админка  ◀────── Координатор/методист    │
                 └──────────┬────────────────────┬───────────────┘
                            │                    │
                     GitHub API/Webhooks   Google Drive/Docs API
                     (ProviderInput #1)    (планируемый ProviderInput)
                            │                    │
                            └─────────┬──────────┘
                                      │
                        ┌─────────────┴────────────────┐
                        │   LLM-слой (через Gateway)   │
                        │  local vLLM/Ollama | OpenRouter │
                        └──────────────────────────────┘
                                      │
                             Google Sheets (экспорт ведомости)
```

**Роли и права (RBAC):**

- `student` — в MVP не имеет UI (сдаёт как раньше), получает фидбек комментарием в PR.
- `reviewer` — видит только свою очередь и работы назначенных студентов.
- `coordinator` — видит весь курс: ведомость, нагрузку, просрочки, может переназначать.
- `admin` — рубрики, интеграции, конфиг LLM-роутинга, аудит.

### Почему такой стек (обоснование для жюри)

| Слой | Выбор | Почему |
|---|---|---|
| Backend | Python 3.11 + FastAPI + SQLAlchemy 2 + Pydantic v2, менеджер пакетов **uv** | Один язык с ML-частью, async, автогенерация OpenAPI → фронт не ждёт бэк; uv даёт воспроизводимый lock и быструю установку на хакатоне |
| Очередь | **arq** + Redis | Async-native, стартует за 5 минут против получаса Celery; на хакатоне это решает |
| БД | PostgreSQL 16 + pgvector | JSONB для гибких рубрик + вектора для дубликатов без второй БД |
| Frontend | React + Vite + TS + shadcn/ui | Скорость сборки UI, готовые компоненты, diff-viewer из коробки |
| Локальный LLM | vLLM (или Ollama на слабом железе) | OpenAI-совместимый API → один клиент на оба маршрута; **нужны logprobs** для детектора |
| Внешний LLM | OpenRouter | Один ключ, смена модели без кода, дешёвые модели под массовые задачи |
| Оркестрация | Свой код (state machine + arq) | n8n рассматривали: удобно демонстрировать, но плохо версионируется и тестируется; оставляем n8n как опцию для «клиентских» интеграций |

### Стандарты кода бэкенда

- **Один сервис, модульная структура.** `ingest`, `assignment`, `review`, `ai` (детектор + LLM-слой) — пакеты внутри одного FastAPI-приложения, а не микросервисы. Границы держатся на уровне модулей и интерфейсов; разнести на сервисы можно позже без переписывания логики.
- **Меньше сущностей.** Мало файлов и классов, но грамотно структурированных; заглушек под нереализованные части не держим. Готовые библиотеки (клиент GitHub и т.п.) не переписываем с нуля.
- **Зависимости — только uv**, комментарии в коде — только там, где фиксируют неочевидное внешнее ограничение.
- **Продакшн-практики FastAPI.** Роутеры по доменам, `Depends` для аутентификации и сессии БД, Pydantic-схемы отделены от ORM-моделей, бизнес-логика в сервисном слое, `async` по всему I/O.
- **Единый контракт входа.** `Review Agent` и `AI-Detection` принимают только `SubmissionBundle` — источник заперт в `Ingestion`.

## 5. Ingestion: SubmissionProvider и единая модель сдачи

`Ingestion` — модуль Python-бэкенда (как `Review` и `AI-Detection`), а не отдельный сервис. Его задача одна: принять ссылку от пользователя или вебхука и вернуть `SubmissionBundle`.

### 5.0 SubmissionProvider

Провайдеры собраны в подпакете `ingest/providers/` как самостоятельные классы поверх
готовых клиентов (GitHub — на `githubkit`). Контракт один:

```python
class SubmissionProvider(ABC):
    source: ClassVar[SubmissionSource]

    async def fetch(self, link: str, *, context: IngestContext) -> SubmissionBundle: ...
```

`fetch` делает и обращение к источнику, и нормализацию — отдельного шага `normalize`
и промежуточного `RawSubmission` нет. Провайдер выбирается **явно**:
`IngestService.ingest(link, source, *, context=...)` берёт его из словаря по `source`,
по ссылке источник не угадывается. `IngestContext` несёт то, что из ссылки не вывести
(`assignment_id`, `deadline_at`, id студента). Конфиг — `IngestConfig` в `config.py`,
переменные окружения `INGEST_*`.

Дальше по стеку — Format Gate, Assignment, Review Agent, AI-Detection — источник
неизвестен, все работают только с `SubmissionBundle`.

**Реализован один провайдер — GitHub.** Новый источник (GitLab MR, Google Docs,
Stepik) = новый класс `SubmissionProvider` в `ingest/providers/` + его конфиг в
`config.py`; заглушек под нереализованные источники не держим.
`scripts/ingest_pr_example.py` прогоняет весь путь на реальном PR.

### 5.1 Канонический объект

`SubmissionBundle` сделан так, чтобы его целиком отдавать LLM: он описывает
**изменение** и минимум контекста вокруг, а тела файлов живут за `content_ref` и
подтягиваются по требованию. Модель провайдеро-независима: git PR/MR и Google Doc
кладутся в одни и те же поля.

`SubmissionBundle` (`ingest/models.py`): `submission_id`, `source`, `origin_url`,
`student_ref` (внутренний id, не ФИО), `submitted_at`/`deadline_at`, `base_ref`/`head_ref`,
`artifacts` — только файлы, затронутые изменением, `revisions` — коммиты для форензики,
`repo` — компактная карта окружающего кода.

**Экономия токенов — три правила:**

1. **Никаких дублей.** Нет ни копии текста файла отдельно от диффа, ни общего диффа целиком.
2. **Дифф вместо тел.** У `Artifact` есть `diff` и `changed_ranges`; `excerpt` (полный
   текст) кладётся, только если файл меньше `excerpt_max_bytes`, иначе большие файлы
   едут diff-only, полный текст — по `content_ref` (тул `get_file`, §6.3).
3. **Карта, а не дерево.** `RepoContext.files` — плоский список путей на head без
   метаданных, с ограничением `max_context_files` и флагом `truncated`.

`Artifact.role` (`solution` / `evidence` / `tooling` / `noise`) — грубая пометка от
ingest, чтобы агент тратил токены на `solution` и пропускал `noise`. `changed_ranges`
(1-based, разобраны из `patch` через `unidiff`) — якорь для кликабельных цитат: агент
возвращает `(path, start, end)`, код валидирует против полного текста.

### 5.2 GitHub-провайдер (итерация 1)

Клиент — `githubkit` (async, типизированный, на нашем же `httpx` + `pydantic`), свой
HTTP-клиент не пишем. Токен из `INGEST_GITHUB__TOKEN` (в проде — GitHub App с правами
`contents:read`, `pull_requests:write`, `metadata:read`); без токена — анонимно с лимитом
60 запросов/час. Тянем PR-метаданные, изменённые файлы с `patch` (он же дифф файла),
git-tree на head, историю коммитов со статистикой (`additions`/`deletions` — для
форензики); blob'ы качаем только под `excerpt`, в пределах `excerpt_max_bytes`.
Webhook (`pull_request.opened|synchronize`) — точка входа в проде; сейчас — явный
`POST /review` по ссылке.

### 5.3 Google Docs провайдер (планируется, в коде нет)

- Service account + Drive API, документ расшарен на её адрес (или студент сдаёт «доступ по ссылке на чтение» — допущение из разбора).
- Экспорт: `files.export` → `text/html` (сохраняем структуру заголовков и списков) + `text/plain` для offset'ов.
- **Drive Revisions API** — золото для детектора: история ревизий показывает «взрывные вставки» (несколько тысяч символов за одну ревизию = вероятная вставка из чата с моделью). Это самый честный не-вероятностный сигнал, который у нас есть.

### 5.4 Новые провайдеры (GitLab, Stepik и другие)

Новый источник = новый класс `SubmissionProvider` (`fetch`) в `ingest/providers/`,
запись в словарь провайдеров и его конфиг в `src/avito_reviewer/config.py`. Он
принимает ссылку и отдаёт `SubmissionBundle`; остальные 90% системы не меняются. Это
и есть ответ на критерий «масштабируемость без переработки архитектуры».

### 5.5 Что показал репозиторий примеров

Разбор `ai-talent-hub-avito/homework_examples` (9 направлений, 51 офисный файл, 27
файлов Go, 22 Python, 2 ноутбука) заставил уточнить слой нормализации — наивное
«прочитали файлы и отдали модели» не работает:

- **Классификатор артефактов и денилист шума.** В «хорошем решении» курса LLM лежит
  `mlruns/` на 314 файлов трекинга MLflow — выхлоп инструмента, не работа студента.
  Туда же `go.sum`, `__pycache__`, `.venv`, миграции. Каждый артефакт классифицируется:
  `solution` (идёт в ревью), `evidence` (учитывается по факту наличия), `noise` (никуда),
  `tooling` (исключён и из детектора ГенИИ).
- **Стриппинг ноутбуков.** Хорошее решение GO — 17 файлов, ~6 600 токенов; курс LLM с
  4 файлами (ноутбуки с сохранёнными выводами и base64-картинками) — **~116 000**.
  Разница в двадцать раз вся в `.ipynb`: код и markdown идут целиком, текстовые выводы —
  с обрезкой, картинки → плейсхолдер `[plot: eval_loss]`. Без этого одна работа съедает
  весь бюджет прогона.
- **Мультифайловые сдачи разных форматов.** `product/Пример ДЗ 5` — решение это `.docx`
  и `.xlsx` вместе, оценивать надо совместно; нужны парсеры `python-docx`, `openpyxl`,
  `pdftotext`, `nbformat` — на всех 51 офисных файлах репозитория отрабатывают без ошибок.
- **Таблицы требуют отдельного разбора.** `tech_QA` — решения это копии Google-шаблона
  на сотни строк, из которых заполнены единицы; нормализатор должен находить строку
  заголовков и отсекать фантомные строки. `product_business_models` — финмодель, где
  важны и формулы, и значения: захардкоженное число там, где ждут формулу, — сигнал сам по себе.
- **Кумулятивные задания.** GO — `task1.md`..`task3.md`, три этапа одной работы в одном
  репозитории; `Submission` привязывается к этапу (`assignment.parent_id`,
  `submission.stage`), и ревью третьего этапа видит, что первые два не сломаны.
- **Условие иногда лежит внутри решения** (`data_science/…/task.md`) — нормализатор
  должен отличать его от самого решения.

## 5А. Format Gate — проверки без единого токена

Самое неожиданное открытие в репозитории: **условия сами содержат жёсткие формальные требования**, которые проверяются кодом и не требуют модели вообще.

| Курс | Требование из условия | Как проверяем |
|---|---|---|
| product_fraud | «Объём: не более 3-х страниц (без приложений); при нарушении объёма работа может не проверяться» | Счёт страниц из `.docx` / `.pdf` |
| product_fraud | «Размер шрифта — 11 пунктов, Arial; для таблиц — 10 пунктов. Межстрочный интервал — 1,15–1,5» | Стили абзацев через `python-docx` |
| product_fraud | «Оформите работу с доступом на редактирование: должна быть видна история изменений, иначе работа принята не будет» | Drive API: доступ + непустая история ревизий |
| tech_QA | «Требуемое количество тест-кейсов — 21… не более 3 на один функционал» | Подсчёт строк по колонке «Функционал» |
| tech_QA | «Каждый обязательный атрибут тест-кейса должен быть описан в отдельной ячейке» | Проверка набора колонок |
| tech_QA | «Отклонение от формата не будет приниматься ревьюерами на проверку» | Блокирующий статус до ревью |
| GO | `GET /ping` → `200` и `{"message":"pong"}`; `HEAD /healthcheck` → `204`; лог `Shutting down service-courier`; флаг `--port` | Запуск в контейнере + smoke-тесты |
| product_fraud | «Досдача в течение 1 дня после дедлайна — штраф −1 балл; позже — 0 баллов» | Арифметика по `submitted_at` |

Отсюда — обязательный шаг конвейера **перед** любым обращением к модели:

```
normalized → FORMAT GATE ──┬─ pass    → скраб ПДн → анализы
                           └─ warn    → анализы, и непройденное названо в карточке
```

> **Разошлось с кодом намеренно.** В реализации статуса `blocked` нет: гейт
> сообщает, но не запрещает. Замысел «не принято по формату — модель не
> запускается» экономил токены ценой того, что студент за одну недостающую
> строку в логе не получал ни слова о сделанном хорошо. Проверки остались все,
> изменилось только то, что за ними следует — см. `docs/handover-backend.md`.

Экономика (не принятая по формату работа не должна стоить токенов), совпадение с тем,
что ревьюеры и так делают первым действием, и точность — формальные факты
(«18 тест-кейсов вместо 21») детерминированы, отдавать их на откуп модели значит
превращать точный ответ в вероятностный. Результат гейта — структурированные факты,
которые подмешиваются в контекст ревью-агента: модели не нужно считать тест-кейсы,
ей сообщают, что их 18 при требуемом 21.

## 6. Рубрика и ревью-агент

Ревью-агент — модуль того же Python-бэкенда. На входе у него только `SubmissionBundle` (после скраба ПДн) и скомпилированная рубрика; других источников данных у него нет.

### 6.0 Rubric Compiler: условия приходят в четырёх разных формах

В репозитории нет единого формата критериев. Их как минимум четыре:

| Форма | Пример | Особенность |
|---|---|---|
| **Таблица с баллами** | system_design, лаба 1: 9 критериев, макс. 6 баллов, дробные веса 0.5, зачёт с 4 | Есть колонки «макс.» и «мин.» — минимум обязателен для зачёта |
| **N вопросов × фиксированный балл** | data_analysis ДЗ2: 5 вопросов по 2 балла с якорями 0 / 1 / 2 | Якоря словесные, готовы к переносу в промпт как есть |
| **Чек-лист DoD без баллов** | GO task1–3: «что нужно сделать» с точными приёмочными признаками | Баллов нет вообще — шкалу надо задать методисту |
| **Формат + количество + штрафы** | tech_QA, product_fraud | Половина критериев формальная, уходит в Format Gate |

Поэтому между «загрузили условие» и «рубрика готова» стоит отдельный шаг — **Rubric Compiler**: LLM разбирает документ условия и предлагает структурированную рубрику, методист подтверждает или правит **один раз на задание**. Это единственное место, где галлюцинация модели дорого стоит, поэтому здесь человек в цикле обязателен и по умолчанию.

У system_design, лаба 2, в условии есть блок «Тест-кейсы (проверочные пункты для
преподавателя)» — готовый список конкретных проверок. Он ложится один в один в
`checks[]` критерия и становится якорем для цитат; такие блоки стоит искать в каждом
условии в первую очередь.

### 6.1 Рубрика как данные, а не как промпт

Схема сделана так, чтобы вместить все четыре формы из §6.0. Пример — реальная лаба 1 по системному дизайну:

```json
{
  "assignment_id": "sysdesign-lab1",
  "scale": { "total_max": 6, "pass_threshold": 4, "step": 0.5 },
  "late_policy": { "grace_days": 1, "penalty_per_grace": 1, "after": "zero" },
  "format_gate": {
    "blocking": [
      { "check": "revision_history_visible", "source": "gdocs" }
    ],
    "warning": [
      { "check": "max_pages", "value": 3 },
      { "check": "font", "family": "Arial", "size_pt": 11, "table_size_pt": 10 }
    ]
  },
  "criteria": [
    {
      "id": "c1",
      "title": "Выполнена декомпозиция по двум и более признакам",
      "max_score": 1, "min_score_for_pass": 1,
      "evidence_required": true,
      "checks": [
        "названы минимум два признака декомпозиции",
        "для каждого признака показан результат разбиения"
      ],
      "anchors": { "0": "признак один или не назван", "1": "два и более, с результатом" }
    },
    {
      "id": "c5",
      "title": "Построена диаграмма C4 (контекстная и компонентная)",
      "max_score": 1, "min_score_for_pass": 1,
      "evidence_required": true,
      "checks": ["есть контекстная диаграмма", "есть компонентная диаграмма одного контейнера"]
    }
  ]
}
```

Три вещи, которых не было в первой версии и которые появились после разбора репозитория:

- `min_score_for_pass` — в system_design у части критериев есть колонка «мин. балл», и зачёт не сводится к сумме: провал по обязательному критерию не компенсируется другими.
- `step: 0.5` — баллы дробные, агрегатор обязан округлять по правилу задания, а не как получится.
- `checks[]` — те самые «проверочные пункты для преподавателя» из условия. Модель отвечает по каждому пункту отдельно, и это резко снижает разброс между прогонами.

Для GO, где баллов в условии нет вовсе, Rubric Compiler превращает пункты «что нужно сделать» в критерии с равными весами и помечает их `auto_verifiable: true` — такие проверяются smoke-тестами, а не моделью.

Рубрика редактируется в админке. Промпт **генерируется из рубрики**, а не пишется руками под каждое задание. Добавить курс = добавить JSON.

### 6.2 Контракт вывода агента

Structured output (JSON Schema), один вызов на критерий или батч 3–5 критериев (компромисс качество/цена):

```json
{
  "criterion_id": "c1",
  "score": 17,
  "confidence": 0.72,
  "verdict": "Контракт соблюдён, но ошибки маппятся в codes.Internal без разбора",
  "evidence": [
    { "artifact": "internal/handler/order.go", "start_line": 44, "end_line": 58,
      "quote": "return nil, status.Error(codes.Internal, err.Error())" }
  ],
  "student_feedback": "Хендлеры собраны аккуратно... давай докрутим маппинг ошибок:",
  "improvement_hint": "Ошибки валидации стоит отдавать как InvalidArgument",
  "needs_human_attention": false
}
```

**Жёсткие правила, зашитые в архитектуру:**

- `evidence` пустой → результат помечается `needs_human_attention=true` и **не показывается как готовый вердикт**. Модель без цитаты не имеет права ставить оценку.
- Цитата валидируется программно: строка реально существует в артефакте. Не совпало — критерий уходит на ретрай, потом к человеку. Это отсекает основную часть галлюцинаций.
- Итоговый балл **считает Python**, не модель. LLM оценивает критерий, арифметику мы ей не доверяем.
- `confidence < 0.6` или разброс между двумя прогонами > 15% → флаг «спорно» в UI.

### 6.3 Итеративный чат ревьюера с моделью

Чат привязан к `review_run_id` и работает как агент с тулами:

| Тул | Что делает |
|---|---|
| `get_file(path, lines?)` | читает артефакт сдачи (после скраба) |
| `get_diff(path?)` | отдаёт diff |
| `get_criterion(id)` | текст критерия и якорей |
| `search_submission(query)` | поиск по работе |
| `propose_review_patch(criterion_id, score?, verdict?, feedback?)` | **предлагает** изменение черновика |

`propose_review_patch` ничего не меняет сам — он рисует ревьюеру дифф черновика с кнопками «Применить / Отклонить». Модель предлагает, человек решает. Каждое применение пишется в `review_revisions` с `author_type='ai_assisted'`.

Типовые реплики, под которые оптимизируем: «обоснуй балл по критерию 2», «студент писал, что тесты падают из-за окружения — учти», «сделай фидбек мягче», «проверь, есть ли обработка контекста в воркерах».

## 7. AI-Detection (модуль бэкенда)

### 7.1 Принцип

Один LLM-детектор — это гадание. Мы строим **ансамбль из сигналов разной природы**, где два из четырёх вообще не вероятностные. Детектор — тоже модуль Python-бэкенда и получает на вход тот же `SubmissionBundle`, что и ревью-агент; отдельного обращения к источнику у него нет.

```
                  ┌──────────────────────────────┐
   Bundle ───────▶│  1. Форензика источника      │  вес 0.35
                  │  git: 1 коммит на 800 строк, │  (детерминированно)
                  │  интервалы, порядок файлов;  │
                  │  Docs: revision-всплески     │
                  ├──────────────────────────────┤
                  │  2. Перплексия (LOCAL)       │  вес 0.25
                  │  logprobs малой модели,      │
                  │  burstiness по окнам         │
                  ├──────────────────────────────┤
                  │  3. Стилометрия / эвристики  │  вес 0.15
                  │  плотность комментариев,     │
                  │  «идеальность», клише,       │
                  │  отсутствие TODO/мусора      │
                  ├──────────────────────────────┤
                  │  4. LLM-judge со спанами     │  вес 0.25
                  │  обязан вернуть цитаты       │
                  └──────────────┬───────────────┘
                                 ▼
                   Калибровка → score 0..1 + доверительный
                   интервал + список спанов с обоснованием
```

### 7.2 Почему форензика — главный вес

Признаки, которые почти не подделываются случайно: вся работа одним коммитом «init»,
900 добавленных строк за 4 минуты, коммиты каждые 20 секунд подряд ночью, файлы в
порядке, обратном зависимостям (git); ревизия, добавившая 4200 символов за один шаг
при среднем размере ревизии 80 символов (Google Docs). Дёшево, детерминированно и
объяснимо человеческим языком — важнее, чем чистая точность, раз по ТЗ сигнал не
доказательство и на балл не влияет автоматически.

### 7.3 Перплексия локально

Малая модель (Qwen2.5-0.5B / rugpt3-small) на vLLM с `logprobs=1`, окна по 256 токенов
со сдвигом 128: средняя NLL и burstiness (дисперсия NLL между окнами) — человеческий
текст «рваный», сгенерированный подозрительно ровный. Обязана быть локальной: нужны
logprobs, которых внешние провайдеры почти не отдают, и объём токенов большой.

### 7.4 Вывод в UI

```json
{
  "overall_score": 0.71,
  "confidence_band": [0.58, 0.83],
  "verdict_label": "средняя вероятность",
  "limitations": "Короткие фрагменты (<200 символов) не оцениваются. Шаблонный код из методички исключён.",
  "spans": [
    { "artifact": "README.md", "start": 1204, "end": 1890,
      "signals": ["low_perplexity", "llm_judge"], "score": 0.86,
      "reason": "Равномерно низкая перплексия + характерные обороты «Важно отметить, что»" },
    { "artifact": "internal/service/order.go", "start": 0, "end": 640,
      "signals": ["git_forensics"], "score": 0.79,
      "reason": "Файл 640 строк добавлен одним коммитом за 3 минуты; в остальных файлах средний коммит 40 строк" }
  ]
}
```

**Обязательный анти-фактор:** шаблонный/сгенерированный фреймворком код (`go.sum`, миграции, `*_pb.go`, boilerplate из методички, все 314 файлов `mlruns/`) исключается из анализа по allowlist — иначе детектор будет ловить самого себя.

### 7.5 Политика курса по ИИ уже написана — и она не бинарная

В условии `product_fraud` есть отдельный блок:

> «На этапах, где ключевой навык — самостоятельный анализ, критическое мышление и синтез данных, **необоснованное** использование ИИ-инструментов будет считаться нарушением и повлечёт снижение баллов. **Если вы использовали ИИ — укажите это в работе и опишите, как именно.**»

Из этого следуют три вывода, которые меняют дизайн детектора: запрещено не
использование, а несогласованное использование; история изменений — требование
самого курса, не наш обходной приём; вес сигнала зависит от критерия
(`ai_sensitive: true`) — сгенерированный boilerplate в `docker-compose.yaml` и
сгенерированная карта рисков разные события.

Правильный вывод детектора — не «сгенерировано / не сгенерировано», а матрица:

| | Сигнал есть | Сигнала нет |
|---|---|---|
| **Студент заявил ИИ** | Норма. Показываем ревьюеру заявление и сигнал рядом: совпадает ли описанное с найденным | Норма, ничего не показываем |
| **Студент не заявил** | **Главный случай.** Именно это ревьюер должен увидеть первым | Норма |

В конвейер это добавляет дешёвый детерминированный шаг — поиск блока-декларации об ИИ
в работе, его текст выводится в панель рядом со спанами: одна строка кода превращает
«подозрение» в проверяемое расхождение между заявленным и найденным.

Клик по спану подсвечивает фрагмент в левом вьювере; кнопки «Подтвердить» / «Отклонить»
пишут решение ревьюера в БД — это же датасет для будущей калибровки порогов.

## 8. LLM-слой: PrivacyGateway и роутинг

### 8.1 Единая точка выхода

```python
class PrivacyGateway:
    async def complete(
        self,
        prompt: PromptSpec,
        *,
        task: TaskKind,               # REVIEW | DETECT | CHAT | NER | EMBED
        data_class: DataClass,        # PUBLIC | INTERNAL | CONTAINS_PD
        route_policy: RoutePolicy,    # LOCAL_ONLY | EXTERNAL_AFTER_SCRUB
    ) -> LLMResponse
```

**Архитектурное правило:** ни один сервис не импортирует SDK провайдера. Только `PrivacyGateway`. Проверяется линт-правилом в CI (`import openai` вне модуля gateway = fail). Это то, что превращает «мы обещали не сливать ПДн» в проверяемое утверждение.

### 8.2 Конвейер обезличивания

```
исходный текст
   │
   ├─▶ 1. РЕГУЛЯРКИ (детерминированно, высокий recall)
   │     email, телефон, @telegram, паспорт, СНИЛС, ИНН,
   │     git author/committer, URL с ФИО, ссылки на профили
   │
   ├─▶ 2. NER (ЛОКАЛЬНАЯ модель, наружу никогда)
   │     Natasha/slovnet для русских ФИО, spaCy для латиницы
   │
   ├─▶ 3. КОД-СПЕЦИФИКА
   │     заголовки лицензий с именами, .env, хардкод-креды,
   │     author-теги в докстрингах
   │
   ├─▶ 4. ПСЕВДОНИМИЗАЦИЯ (не удаление!)
   │     Иван Петров → [PERSON_1],  ivan@mail.ru → [EMAIL_1]
   │     map хранится в Redis по request_id, TTL 1 час
   │     ↳ стабильные токены сохраняют связность текста для модели
   │
   ├─▶ 5. ВАЛИДАТОР ОСТАТОЧНОГО РИСКА
   │     повторный проход другим набором правил;
   │     нашли high-confidence ПДн → маршрут ПРИНУДИТЕЛЬНО
   │     понижается до LOCAL_ONLY (fail-safe, не fail-open)
   │
   ├─▶ 6. ВЫЗОВ ПРОВАЙДЕРА
   │
   ├─▶ 7. РЕГИДРАТАЦИЯ ОТВЕТА
   │     [PERSON_1] → Иван Петров (только внутри нашего периметра)
   │
   └─▶ 8. АУДИТ
         request_id, provider, model, route, data_class,
         redactions_count, prompt_sha256, tokens, cost, latency
         ⚠ сырой промпт НЕ сохраняется, только хэш
```

Псевдонимизация вместо вырезания — принципиально: модель должна понимать, что «[PERSON_1] в README ссылается на [PERSON_1] в коде», иначе качество ревью падает.

### 8.3 Матрица роутинга

| Задача | Маршрут | Модель (пример) | Почему |
|---|---|---|---|
| NER для ПДн | **LOCAL_ONLY** | slovnet / Natasha | Отправлять ПДн наружу, чтобы их найти — абсурд |
| Перплексия | **LOCAL_ONLY** | Qwen2.5-0.5B (vLLM) | Нужны logprobs, огромный объём токенов, ~0 ₽ |
| Эмбеддинги (дубликаты) | **LOCAL_ONLY** | bge-m3 / e5-large | Объём + это по сути весь корпус работ |
| Ревью по критериям | EXTERNAL_AFTER_SCRUB | claude-sonnet / gpt-4o-mini через OpenRouter | Качество рассуждений критично для доверия |
| LLM-judge ГенИИ | EXTERNAL_AFTER_SCRUB | gpt-4o-mini | Дёшево, нужна только классификация со спанами |
| Чат ревьюера | EXTERNAL_AFTER_SCRUB | claude-sonnet | Интерактив, качество диалога |
| Генерация ToV-фидбека | EXTERNAL_AFTER_SCRUB | gpt-4o-mini | Стилистика, дёшево |

Оба маршрута — **OpenAI-совместимый клиент**, отличаются только `base_url` и ключом. Переключение локальный ↔ внешний = одна строка в конфиге. Это же даёт демо-фичу: «показываем работу полностью на локальной модели, без единого внешнего запроса».

### 8.4 Экономика прогона

Ориентир из разбора: **< 5–10 ₽ за работу**. После замеров на реальном репозитории картина конкретнее.

| Тип работы | Токенов после нормализации | Ревью | Judge | Итого |
|---|---|---|---|---|
| GO, этап 1–3 | ~7k | ~1 ₽ | ~0.4 ₽ | **~1.5 ₽** |
| System design, одна лаба | ~5k | ~0.8 ₽ | ~0.3 ₽ | **~1.1 ₽** |
| Продуктовое ДЗ (docx + xlsx) | ~8k | ~1.2 ₽ | ~0.4 ₽ | **~1.6 ₽** |
| tech_QA (21 тест-кейс в таблице) | ~6k | ~1 ₽ | ~0.3 ₽ | **~1.3 ₽** |
| Курс LLM **без** стриппинга ноутбука | ~116k | ~15 ₽ | ~6 ₽ | **~21 ₽** ⚠ |
| Курс LLM **со** стриппингом | ~14k | ~2 ₽ | ~0.7 ₽ | **~2.7 ₽** |

Перплексия и эмбеддинги локальные — ноль. Профили работы и ревьюера для распределения (§9.2) — ещё ~0.2 ₽ на сдачу.

Вывод, который стоит вынести в питч: **бюджет ломает не сложность разбора, а неотфильтрованный мусор.** Одна работа с сырым `.ipynb` стоит как четырнадцать нормальных. Поэтому нормализатор и денилист — не гигиена, а статья экономии.

Остальные механики удержания цены: кэш рубрики и условия (prompt caching — условие одно на весь поток), батчинг критериев по 3–5, Format Gate до модели, лимит на размер диффа с деградацией до ревью по ключевым файлам.

## 9. Assignment Engine (распределение)

> **Пересмотрено.** В первой версии здесь было «никакого LLM». Это было слишком грубо: без семантики работы распределение вырождается в балансировку счётчиков и игнорирует то, о чём работа вообще. Ниже — гибрид.

### 9.1 Разделяем два разных вопроса

| Вопрос | Кто отвечает | Почему так |
|---|---|---|
| **Что это за работа и что за ревьюер?** | LLM и эмбеддинги | Требует понимания содержания: темы, стек, сложность, зона риска |
| **Кому конкретно её отдать?** | Детерминированный солвер | Нужны воспроизводимость, объяснимость, пересчёт при болезни ревьюера |

LLM работает **вне горячего пути**: он строит признаки один раз на сдачу и периодически на ревьюера. Выбор ревьюера — функция от готовых векторов и операционных ограничений. Это даёт персонализацию, но оставляет распределение объяснимым: координатор должен уметь ответить студенту «почему тебя проверяет именно он», а ревьюеру — «почему тебе дали эту работу».

### 9.2 Профили, которые строит LLM

`WorkProfile` (1 вызов на сдачу, ~1k токенов): `topics`, `stack`, `complexity` (0..1),
`risk_criteria`, `special_needs`, `est_review_minutes` — прогноз трудоёмкости, а не
«одна работа = один слот». Главный выигрыш от семантики: работа по GO на 6k токенов
и работа по курсу LLM с ноутбуком на 116k — это не «две работы», это 20 минут и
полтора часа.

`ReviewerProfile` (пересчёт раз в сутки по истории ревью): `strength_vector` —
эмбеддинг тем с минимальной правкой, `weak_topics`, `tov`, `median_minutes_per_work`
(фактическая скорость, не декларируемая), `onboarding` (методист смотрит первые
работы нового ревьюера).

`StudentProfile`: `recurring_errors` (что валится из ДЗ в ДЗ), `last_reviewer_id`,
`growth_area`.

### 9.3 Решение принимает солвер

```python
def match_score(r: ReviewerProfile, w: WorkProfile, s: StudentProfile) -> float:
    if r.minutes_committed + w.est_review_minutes > r.week_capacity_minutes: return -inf
    if conflict_of_interest(r, w): return -inf          # соавтор коммитов
    return (
        + 1.0 * cosine(r.strength_vector, w.topic_vector)   # ← семантика от LLM
        + 0.6 * covers(r.skills, w.special_needs)
        + 0.4 * continuity(r, s.last_reviewer_id)           # тот же ревьюер видит динамику
        + 0.3 * tov_fit(r.tov, s.growth_area)               # персонализация фидбека
        - 0.8 * load_ratio(r)                               # операционка
        - 0.5 * deadline_risk(r, w)
        + 0.2 * fairness_bonus(r)
        - 0.7 * onboarding_penalty(r, w.complexity)         # сложное — не новичку
    )
```

**Два режима работы:**

- **Batch (основной).** В материалах курса зафиксировано: «проверка начинается после окончания дедлайна и занимает не более 7 дней». Значит распределяется не поток по одному, а весь поток разом. Это классическая задача о назначениях — решаем венгерским алгоритмом или min-cost flow по матрице `match_score`, что даёт глобальный оптимум вместо жадного разбора в порядке поступления.
- **Online (для курсов с rolling-дедлайнами).** Тот же скор, жадный выбор, периодическая ребалансировка.

### 9.4 Где LLM всё-таки заходит в само решение

Одно место, и в советующей роли: **предложение переназначить**. Если ревью-агент вернул низкую уверенность или разброс между прогонами, работа помечается как пограничная, и координатор видит карточку: «предлагаю передать сильному ревьюеру, потому что вердикт по критерию 4 неустойчив». Кнопка «Применить» — за человеком. LLM объясняет, солвер считает, координатор решает.

### 9.5 Что осталось детерминированным намеренно

Расписание не должно менять ответ между запусками. Если координатор в 10:00 и в 10:05 видит разные распределения одного и того же пула — он перестаёт пользоваться системой. Поэтому: профили кэшируются и версионируются, солвер получает их на вход как данные, каждое назначение хранит `explain` — вклад каждого слагаемого в скор, чтобы карточка «почему так» открывалась без повторного вызова модели.

## 10. Схема данных (PostgreSQL)

```
courses ──< assignments ──< rubrics ──< rubric_criteria
                │
                └──< submissions ──< submission_artifacts
                        │            └ (path, kind, content_ref, lang, size)
                        ├──< submission_history_events
                        │       (commit/revision: ts, author_hash, added, removed)
                        │
                        ├──< review_runs ──< review_criterion_results ──< evidence_citations
                        │       │
                        │       ├──< review_chat_messages  (role, content, tool_calls)
                        │       └──< review_revisions      (author_type, diff, ts)
                        │
                        ├──< ai_detection_runs ──< ai_detection_spans
                        │                              └ (artifact, start, end, signals[],
                        │                                 score, reason, reviewer_verdict)
                        │
                        └──< review_final  (score, feedback, approved_by, approved_at)

format_gate_results (submission_id, check_id, status, expected, actual, blocking)
work_profiles     (submission_id, topics[], stack[], complexity,
                   est_review_minutes, risk_criteria[], topic_vector)
reviewer_profiles (reviewer_id, strength_vector, weak_topics[], tov,
                   median_minutes_per_work, onboarding, computed_at)
assignment_explain (submission_id, reviewer_id, term, contribution)

students (внутр. id, внешние handle'ы, БЕЗ лишних ПДн)
reviewers (capacity_minutes, max_wip, skills[])
assignments_queue (submission_id, reviewer_id, assigned_at, due_at, state)
llm_call_audit (request_id, provider, model, route, data_class,
                redactions, prompt_sha256, tokens_in/out, cost, latency)
sheets_sync_log (submission_id, row, synced_at, status)
submission_embeddings (vector) ← pgvector, для дубликатов
```

Состояния сдачи (state machine):

```
received → normalized → scrubbed → analyzing → draft_ready
   → in_review → (needs_changes ⇄ in_review) → approved → exported
                                   ↘ failed → manual_fallback
```

`manual_fallback` — обязательное состояние: если LLM недоступен или упал, ревьюер получает работу с пустым черновиком и всё равно может её проверить. Система не должна становиться единой точкой отказа процесса.

## 12. Фронтенд: экраны

### 12.1 Review Workspace — главный экран

Три зоны: работа слева (файлы, дифф, подсветка цитаты), черновик по критериям в
центре с баллом, обоснованием и цитатой на каждый пункт, и справа — признаки ГенИИ
(score, доверительный интервал, спаны с кнопками «Подтвердить/Отклонить»); чат с
моделью — снизу, не перекрывает контекст. Клик по цитате или по спану скроллит и
подсвечивает нужный фрагмент слева; правка балла — инлайн.

(В реализации панель признаков ГенИИ — не третья колонка, а вкладка рядом с
черновиком: см. `docs/handover-frontend.md`, «Review Workspace — две колонки».)

### 12.2 Остальные экраны

- **Inbox ревьюера** — очередь с сортировкой по дедлайну, бейдж «черновик готов», прогресс дня.
- **Карточка студента** — все ДЗ, динамика баллов, история фидбека, флаги ГенИИ по курсу (проваливание в ученика, как вы и хотели).
- **Дашборд координатора** — воронка сдач, просрочки, нагрузка ревьюеров, среднее время проверки, кнопка ребалансировки.
- **Редактор рубрики** — JSON-форма с превью промпта.
- **Аудит** — журнал обращений к LLM: маршрут, модель, число редактирований ПДн, стоимость.

## 13. Безопасность и ответственность

| Риск | Митигация в архитектуре |
|---|---|
| Утечка ПДн во внешний API | `PrivacyGateway` как единственный выход + CI-правило + fail-safe валидатор остаточного риска + `LOCAL_ONLY` для чувствительных задач |
| Галлюцинации в оценке | Обязательные цитаты с программной валидацией; балл считает код; флаг «спорно»; ревьюер утверждает |
| Ложное обвинение в ГенИИ | Advisory-статус, доверительный интервал, явное описание ограничений, allowlist шаблонного кода, кнопка «Отклонить сигнал», отсутствие влияния на балл |
| Недоверие ревьюеров | Показ цепочки рассуждений и цитат, возможность спорить с моделью в чате, полный лог правок |
| Отказ LLM-провайдера | Состояние `manual_fallback`, ретраи с бэкоффом, автопереключение external → local |
| Prompt injection из работы студента | Контент студента передаётся в отдельном блоке с явной разметкой и инструкцией игнорировать директивы внутри; вывод валидируется схемой; тулы агента read-only |
| Несанкционированный доступ | RBAC + скоуп по курсу/назначению; ревьюер не видит чужих студентов |
| Подмена вебхука | Проверка HMAC-подписи GitHub, дедуп по delivery_id |
| Аудируемость оценки | `review_revisions`: кто, когда, что изменил, ai / human / ai-assisted |

Отдельно: **сырые промпты не хранятся**, только SHA-256 и счётчики. PII-map живёт в Redis с TTL и не попадает в долговременное хранилище.

## 14. Метрики эффекта (для критерия «Эффективность»)

| Метрика | Как считаем | Цель |
|---|---|---|
| Время на одну проверку | `approved_at − first_opened_at` | 30 мин → 10–15 мин |
| Доля принятых без правок | `review_revisions` пустые / всего | > 40% |
| Дельта балла AI vs финал | `avg abs(ai_score − final_score)` | < 8 из 100 |
| Ручных действий на работу | счётчик в UI + отсутствие ручного переноса в Sheets | −70% |
| Просроченные проверки | статусы очереди | −50% |
| Время координатора | опрос + число ручных переназначений | 10 ч/нед → 1–2 ч/нед |
| Стоимость прогона | `llm_call_audit.cost` | < 5–10 ₽ |
| Precision детектора ГенИИ | подтверждённые / всего сигналов | > 0.7 на калибровочной выборке |
| CSI студента | опрос по фидбеку | не ниже базового |

Дельта `ai_score` vs `final_score` — самая честная метрика качества и одновременно источник данных для дообучения промптов.

## 15. План на 24–48 часов

### Какое задание брать для демо

ТЗ разрешает выбрать одно задание и один канал. После разбора репозитория рекомендация такая:

**Основное — GO (task1–3), канал GitHub.** Причины: решения компактные (~7k токенов, дешёвый прогон), приёмочные признаки в условии точные до строки лога и формата флага — значит Format Gate и smoke-тесты дают эффектную детерминированную часть демо, три этапа показывают кумулятивную проверку и повторное ревью, а три уровня решений уже разложены по папкам.

**Вторым номером — system_design, лаба 1.** Это markdown в том же GitHub, то есть новый канал не нужен, зато появляется совсем другой тип работы: текстовый документ с диаграммами, дробные баллы, порог зачёта и готовые «проверочные пункты для преподавателя». Одним движением закрывается критерий «масштабируется на другие курсы» — на демо видно, что система работает и с кодом, и с текстом.

**Третьим, если останется время — tech_QA.** Таблица вместо документа, и Format Gate там особенно нагляден: «21 тест-кейс требуется, 18 найдено, по функционалу „Поиск“ их 5 при лимите 3» — ноль токенов, мгновенный вердикт.

Продуктовые направления (`product`, `product_fraud`, `product_business_models`) оставляем на «масштабирование»: там `.docx` и `.xlsx`, отдельные парсеры и другой канал сдачи.

Разделение на 4 потока (backend/ingest, review+LLM, detection+privacy, frontend),
интеграция и сквозной прогон в последней трети времени, буфер на багфиксы и
запасное видео демо в самом конце — план разошёлся с фактическим порядком лишь в
деталях, актуальное состояние в `docs/handover-backend.md` и `docs/handover-frontend.md`.

### Что режем без сожалений

- Аутентификация — один хардкод-логин на роль (не через OAuth).
- Векторный поиск дубликатов — только если остаётся время (это COULD).
- Google Docs и Stepik — не делаем; в коде заглушек под них нет, описаны только в архитектуре как будущие `SubmissionProvider`.
- Мультиязычность UI, мобильная вёрстка, тонкие настройки прав.
- Реальный вебхук — poller надёжнее на демо; вебхук показываем кодом.

### Что нельзя резать

Обязательные функции ТЗ (распределение, ревью по критериям, детектор ГенИИ), **валидация цитат**, **PrivacyGateway**, **панель ГенИИ со спанами** и **Format Gate** — это то, чем решение отличается от «обёртки над ChatGPT». Format Gate добавился в этот список после разбора репозитория: он дешёвый, детерминированный и закрывает половину того, что ревьюер делает руками в первую минуту.

**Закрыто:**

- ~~Доступна ли история ревизий Google Docs?~~ → Курс сам её требует от студента: «должна быть видна история изменений, иначе работа принята не будет».

**Осталось:**

1. Работы приходят как PR в живом репозитории или как архивы/копии, вроде тех, что в примерах (`course-go-avito-<username>-<sha>`)? Имя папки выглядит как выгрузка GitHub Classroom — если так, ingestion идёт через Classroom API, а не через вебхуки PR.
2. Есть ли эталонная разметка: не просто ярлык «слабое / среднее / хорошее», а выставленные баллы по критериям и текст фидбека от реального ревьюера? Без этого нечем измерить расхождение `ai_score` и `final_score` — а это наша главная метрика качества.
3. Как читать ярлыки в примерах: «слабое» — это конкретный балл или диапазон? В `system_design/лаба 1` два слабых решения (`слабое_1`, `слабое_2`) — они равны по баллу или различаются?
4. Ограничения безопасности Авито на внешних LLM-провайдеров: допустим ли OpenRouter вообще, или демонстрировать нужно полностью локальный контур?
5. Кто и как заводит рубрику в проде: методист руками через Rubric Compiler на каждое задание, или условия достаточно единообразны, чтобы компилировать пакетно?
