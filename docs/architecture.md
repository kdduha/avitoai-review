# Avito AI Reviewer — архитектура решения

**Кейс:** AI-помощник ревьюера и координатора образовательных программ Авито (хакатон AITH / TalentHub).
**Формат:** веб-платформа для кураторов и ревьюеров.

Design-документ: описывает целевую форму системы. Расхождения с кодом
намеренны и помечены; фактическое состояние — в `handover-backend.md` и
`handover-frontend.md`.

---

## 0. Опоры решения

Не бот, а рабочее место ревьюера: одна вкладка вместо GitHub + Google Docs + Sheets.

1. **Канонизация сдачи.** `ProviderInput` принимает ссылку (PR, документ,
   страница курса) и отдаёт единый `SubmissionBundle`. Реализован один провайдер
   — GitHub; остальные подключаются как новые реализации того же интерфейса, и
   ничего выше по стеку не меняется.
2. **Дешёвое перед дорогим.** Классификатор артефактов и Format Gate —
   детерминированные проверки, не стоящие ни одного токена.
3. **Grounded-ревью.** LLM выдаёт по каждому критерию вердикт и **обязательную
   цитату** (файл, строки). Итоговый балл считает агрегатор в коде.
4. **Приватный контур.** Единственный выход к внешним LLM — `PrivacyGateway`.
   Прямые вызовы провайдеров запрещены архитектурно и ловятся в CI.

Сквозной принцип: **модель понимает содержание, код принимает решения.** Любая
правка черновика пишется в `review_revisions` с авторством (ai / human /
ai-assisted).

## 1. Что автоматизируем

| Этап | Сейчас | В решении |
|---|---|---|
| Публикация задания и критериев | Методист вручную | Импорт задания + рубрики (одноразово на курс) |
| Ведомость, распределение | Google Sheets вручную | Auto-assignment по нагрузке/капасити/дедлайнам |
| Сдача работы | PR / ссылка на Docs | Webhook + polling |
| Проверка формата | Глазами | Format Gate — детерминированно, до модели |
| Первичное ревью | 30 мин руками | AI-черновик с цитатами → ревьюер за 10–15 мин |
| Проверка на ГенИИ | Не делается системно | Агент-детектор + git/revision-форензика, спаны в UI |
| Обратная связь | Пишется руками | Черновик в нужном ToV, ревьюер правит |
| Фиксация результата | Ручной перенос в Sheets | Автозапись в Sheets + БД |
| Контроль сроков | Ручной пинг | Дашборд просрочек |
| **Итоговая оценка и спорные случаи** | Ревьюер | **Ревьюер** — не автоматизируем (ограничение ТЗ) |

## 2. Акторы и права

- `student` — сдаёт работу, видит свои оценки после утверждения.
- `reviewer` — своя очередь и работы назначенных студентов.
- `methodist` — рубрики, описания заданий, сроки.
- `admin` — интеграции, конфиг LLM-роутинга, аудит, переназначения.

Внешние системы: GitHub API/Webhooks (реализовано), Google Drive/Docs API
(планируется), Google Sheets (экспорт ведомости).

### Стек

| Слой | Выбор | Почему |
|---|---|---|
| Backend | Python 3.11 + FastAPI + SQLAlchemy 2 + Pydantic v2, **uv** | Один язык с ML-частью, async, автогенерация OpenAPI; воспроизводимый lock |
| Очередь | **arq** + Redis | Async-native, стартует за минуты против получаса Celery |
| БД | PostgreSQL 16 + pgvector | JSONB для гибких рубрик + вектора для дубликатов без второй БД |
| Frontend | React + Vite + TS + shadcn/ui | Скорость сборки UI, diff-viewer из коробки |
| Локальный LLM | vLLM (Ollama на слабом железе) | OpenAI-совместимый API → один клиент на оба маршрута; **нужны logprobs** |
| Внешний LLM | OpenRouter | Один ключ, смена модели без кода |
| Оркестрация | Свой код (state machine + arq) | n8n плохо версионируется и тестируется |

### Стандарты кода бэкенда

- **Один сервис, модульная структура.** `ingest`, `assignment`, `review`, `ai` —
  пакеты внутри одного FastAPI-приложения, а не микросервисы.
- **Меньше сущностей.** Мало файлов и классов; заглушек под нереализованные
  части не держим. Готовые библиотеки не переписываем.
- **Зависимости — только uv.** Комментарии — только там, где фиксируют
  неочевидное внешнее ограничение.
- **Продакшн-практики FastAPI.** Роутеры по доменам, `Depends`, Pydantic-схемы
  отдельно от ORM, логика в сервисном слое, `async` по всему I/O.
- **Единый контракт входа.** Review Agent и AI-Detection принимают только
  `SubmissionBundle` — источник заперт в `Ingestion`.

## 4. Сквозной сценарий

```
[1] Студент открывает PR в репозитории курса
[2] GitHub webhook / poll → Ingestion; HMAC-подпись, дедуп по delivery_id
[3] ProviderInput (GitHub): ссылка → SubmissionBundle
        ├─ files[]: путь, язык, содержимое, размер
        ├─ diff: unified diff по base..head
        ├─ history[]: коммиты (время, автор, объём)
        └─ meta: студент, задание, время сдачи vs дедлайн
[3a] Классификатор артефактов: solution / evidence / noise / tooling
        ↳ mlruns/, go.sum, __pycache__ выброшены; .ipynb стриппится
[3b] FORMAT GATE (без токенов): объём, шрифты, число тест-кейсов,
     видимость истории ревизий, smoke-тесты
        ↳ непройденное — факт для модели и строка ревьюеру, не остановка
[4] Assignment Engine: WorkProfile от LLM + солвер по match_score → ревьюер
[5] PrivacyGateway.scrub(bundle) → PII-map в Redis (TTL 1ч)
   ┌────┴──────────────────┬───────────────────────┐
   ▼                       ▼                       ▼
[6a] Static Checks     [6b] Review Agent      [6c] AI-Detection
   └────┬──────────────────┴───────────────────────┘
[7] Aggregator: балл считает КОД. score = Σ (criterion_score × weight),
    штраф за просрочку, confidence-флаги
[8] ReviewDraft → Inbox ревьюера
[9] Review Workspace: цитаты, правка баллов, чат с моделью
        → агент с тулами читает файл → предлагает patch → ревьюер решает
[10] Ревьюер подтверждает/отклоняет сигнал ГенИИ (advisory, на балл не влияет)
[11] «Утвердить» → review_final в БД + комментарий в PR + строка в Sheets
```

## 5. Ingestion: SubmissionProvider и единая модель сдачи

`Ingestion` — модуль бэкенда. Задача одна: принять ссылку и вернуть
`SubmissionBundle`.

### 5.0 SubmissionProvider

Провайдеры — самостоятельные классы в `ingest/providers/` поверх готовых
клиентов (GitHub — `githubkit`).

```python
class SubmissionProvider(ABC):
    source: ClassVar[SubmissionSource]

    async def fetch(self, link: str, *, context: IngestContext) -> SubmissionBundle: ...
```

`fetch` делает и обращение к источнику, и нормализацию — отдельного шага
`normalize` и промежуточного `RawSubmission` нет. Провайдер выбирается **явно**:
`IngestService.ingest(link, source, *, context=...)`; по ссылке источник не
угадывается. `IngestContext` несёт то, что из ссылки не вывести (`assignment_id`,
`deadline_at`, id студента). Конфиг — `IngestConfig` в `config.py`, переменные
`INGEST_*`.

Дальше по стеку источник неизвестен: Format Gate, Assignment, Review Agent,
AI-Detection работают только с `SubmissionBundle`.

Реализован один провайдер — GitHub. Заглушек под нереализованные источники в
коде нет. `scripts/ingest_pr_example.py` прогоняет весь путь на реальном PR.

### 5.1 Канонический объект

`SubmissionBundle` (`ingest/models.py`) описывает **изменение** и минимум
контекста вокруг; тела файлов живут за `content_ref`. Поля: `submission_id`,
`source`, `origin_url`, `student_ref` (внутренний id, не ФИО),
`submitted_at`/`deadline_at`, `base_ref`/`head_ref`, `artifacts` (только
затронутые изменением), `revisions` (коммиты для форензики), `repo` (компактная
карта окружающего кода).

Экономия токенов — три правила:

1. **Никаких дублей.** Ни копии текста файла отдельно от диффа, ни общего диффа.
2. **Дифф вместо тел.** У `Artifact` есть `diff` и `changed_ranges`; `excerpt`
   кладётся только если файл меньше `excerpt_max_bytes`, иначе файл едет
   diff-only, полный текст — по `content_ref` (тул `get_file`, §6.3).
3. **Карта, а не дерево.** `RepoContext.files` — плоский список путей на head,
   ограничен `max_context_files`, с флагом `truncated`.

`Artifact.role` (`solution` / `evidence` / `tooling` / `noise`) — пометка от
ingest, чтобы агент тратил токены на `solution`. `changed_ranges` (1-based, из
`patch` через `unidiff`) — якорь для кликабельных цитат: агент возвращает
`(path, start, end)`, код валидирует против полного текста.

### 5.2 GitHub-провайдер

Клиент — `githubkit` (async, типизированный, на том же httpx + pydantic). Токен
из `INGEST_GITHUB__TOKEN` (в проде — GitHub App с `contents:read`,
`pull_requests:write`, `metadata:read`); без токена анонимный лимит 60
запросов/час. Тянем PR-метаданные, изменённые файлы с `patch`, git-tree на head,
историю коммитов со статистикой; blob'ы качаем только под `excerpt`. Webhook
(`pull_request.opened|synchronize`) — точка входа в проде; сейчас явный
`POST /review` по ссылке.

### 5.3 Google Docs (планируется, в коде нет)

- Service account + Drive API, документ расшарен на её адрес.
- Экспорт: `files.export` → `text/html` (структура заголовков) + `text/plain` (offset'ы).
- **Drive Revisions API** — не-вероятностный сигнал для детектора: несколько
  тысяч символов за одну ревизию = вероятная вставка из чата с моделью.

### 5.4 Новые провайдеры

Новый источник = новый класс `SubmissionProvider` в `ingest/providers/`, запись
в словарь провайдеров, конфиг в `config.py`. Остальные 90% системы не меняются.

### 5.5 Что показал репозиторий примеров

Разбор `ai-talent-hub-avito/homework_examples` (9 направлений, 51 офисный файл,
27 файлов Go, 22 Python, 2 ноутбука) уточнил слой нормализации:

- **Классификатор артефактов и денилист шума.** В «хорошем решении» курса LLM
  лежит `mlruns/` на 314 файлов трекинга MLflow. Туда же `go.sum`, `__pycache__`,
  `.venv`, миграции.
- **Стриппинг ноутбуков.** Хорошее решение GO — 17 файлов, ~6 600 токенов; курс
  LLM с 4 файлами (ноутбуки с выводами и base64-картинками) — **~116 000**.
  Разница вся в `.ipynb`: код и markdown целиком, текстовые выводы с обрезкой,
  картинки → плейсхолдер `[plot: eval_loss]`.
- **Мультифайловые сдачи разных форматов.** `product/Пример ДЗ 5` — решение это
  `.docx` и `.xlsx` вместе; нужны `python-docx`, `openpyxl`, `pdftotext`,
  `nbformat`.
- **Таблицы требуют отдельного разбора.** `tech_QA` — копии Google-шаблона на
  сотни строк, из которых заполнены единицы: нормализатор должен находить строку
  заголовков и отсекать фантомные строки. `product_business_models` — финмодель,
  где важны и формулы, и значения.
- **Кумулятивные задания.** GO — `task1.md`..`task3.md`, три этапа в одном
  репозитории; `Submission` привязывается к этапу (`assignment.parent_id`,
  `submission.stage`).
- **Условие иногда лежит внутри решения** (`data_science/…/task.md`).

## 5А. Format Gate — проверки без единого токена

Условия сами содержат жёсткие формальные требования, проверяемые кодом.

| Курс | Требование из условия | Как проверяем |
|---|---|---|
| product_fraud | «Объём: не более 3-х страниц (без приложений)» | Счёт страниц из `.docx` / `.pdf` |
| product_fraud | «Шрифт 11 пунктов, Arial; таблицы — 10; интервал 1,15–1,5» | Стили абзацев через `python-docx` |
| product_fraud | «Должна быть видна история изменений» | Drive API: доступ + непустая история ревизий |
| tech_QA | «Требуемое количество тест-кейсов — 21… не более 3 на функционал» | Подсчёт строк по колонке «Функционал» |
| tech_QA | «Каждый обязательный атрибут — в отдельной ячейке» | Проверка набора колонок |
| GO | `GET /ping` → `200` и `{"message":"pong"}`; `HEAD /healthcheck` → `204`; лог `Shutting down service-courier`; флаг `--port` | Запуск в контейнере + smoke-тесты |
| product_fraud | «Досдача в течение 1 дня — штраф −1 балл; позже — 0» | Арифметика по `submitted_at` |

```
normalized → FORMAT GATE ──┬─ pass    → скраб ПДн → анализы
                           └─ warn    → анализы, и непройденное названо в карточке
```

> **Разошлось с кодом намеренно.** В реализации статуса `blocked` нет: гейт
> сообщает, но не запрещает. Замысел «не принято по формату — модель не
> запускается» экономил токены ценой того, что студент за одну недостающую
> строку в логе не получал ни слова о сделанном хорошо. Проверки остались все,
> изменилось только то, что за ними следует — см. `handover-backend.md`.

Результат гейта — структурированные факты, которые подмешиваются в контекст
ревью-агента: модели не нужно считать тест-кейсы, ей сообщают, что их 18 при
требуемом 21. Отдавать точный факт на откуп модели значит превращать его в
вероятностный.

## 6. Рубрика и ревью-агент

На входе только `SubmissionBundle` (после скраба ПДн) и скомпилированная
рубрика; других источников данных нет.

### 6.0 Rubric Compiler

Критерии в материалах приходят минимум в четырёх формах:

| Форма | Пример | Особенность |
|---|---|---|
| Таблица с баллами | system_design лаба 1: 9 критериев, макс. 6, веса 0.5, зачёт с 4 | Есть колонки «макс.» и «мин.» |
| N вопросов × фиксированный балл | data_analysis ДЗ2: 5 вопросов по 2 балла | Якоря словесные, готовы к переносу в промпт |
| Чек-лист DoD без баллов | GO task1–3 | Баллов нет вообще — шкалу задаёт методист |
| Формат + количество + штрафы | tech_QA, product_fraud | Половина критериев формальная, уходит в Format Gate |

Между «загрузили условие» и «рубрика готова» стоит **Rubric Compiler**: LLM
разбирает документ условия и предлагает структурированную рубрику, методист
подтверждает или правит **один раз на задание**. Единственное место, где
галлюцинация дорого стоит, поэтому человек в цикле обязателен.

Блоки «Тест-кейсы (проверочные пункты для преподавателя)», встречающиеся в
условиях, ложатся один в один в `checks[]` критерия и становятся якорем для
цитат.

### 6.1 Рубрика как данные

```json
{
  "assignment_id": "sysdesign-lab1",
  "scale": { "total_max": 6, "pass_threshold": 4, "step": 0.5 },
  "late_policy": { "grace_days": 1, "penalty_per_grace": 1, "after": "zero" },
  "format_gate": {
    "blocking": [ { "check": "revision_history_visible", "source": "gdocs" } ],
    "warning": [
      { "check": "max_pages", "value": 3 },
      { "check": "font", "family": "Arial", "size_pt": 11, "table_size_pt": 10 }
    ]
  },
  "criteria": [
    {
      "id": "c1",
      "title": "Выполнена декомпозиция по двум и более признакам",
      "max_score": 1, "min_score_for_pass": 1,
      "evidence_required": true,
      "checks": [
        "названы минимум два признака декомпозиции",
        "для каждого признака показан результат разбиения"
      ],
      "anchors": { "0": "признак один или не назван", "1": "два и более, с результатом" }
    }
  ]
}
```

- `min_score_for_pass` — провал по обязательному критерию не компенсируется
  другими.
- `step: 0.5` — баллы дробные, агрегатор округляет по правилу задания.
- `checks[]` — проверочные пункты из условия; модель отвечает по каждому
  отдельно, это снижает разброс между прогонами.

Для GO, где баллов в условии нет, Rubric Compiler превращает пункты «что нужно
сделать» в критерии с равными весами и помечает `auto_verifiable: true` — такие
проверяются smoke-тестами, а не моделью.

Промпт **генерируется из рубрики**, а не пишется руками. Добавить курс = добавить JSON.

### 6.2 Контракт вывода агента

Structured output (JSON Schema), один вызов на критерий или батч 3–5:

```json
{
  "criterion_id": "c1",
  "score": 17,
  "confidence": 0.72,
  "verdict": "Контракт соблюдён, но ошибки маппятся в codes.Internal без разбора",
  "evidence": [
    { "artifact": "internal/handler/order.go", "start_line": 44, "end_line": 58,
      "quote": "return nil, status.Error(codes.Internal, err.Error())" }
  ],
  "student_feedback": "Хендлеры собраны аккуратно... давай докрутим маппинг ошибок:",
  "improvement_hint": "Ошибки валидации стоит отдавать как InvalidArgument",
  "needs_human_attention": false
}
```

Правила, зашитые в архитектуру:

- `evidence` пустой → `needs_human_attention=true`, вердикт не показывается как
  готовый. Модель без цитаты не имеет права ставить оценку.
- Цитата валидируется программно против текста артефакта. Не совпало — ретрай,
  потом к человеку.
- Итоговый балл считает Python, не модель.
- `confidence < 0.6` или разброс между прогонами > 15% → флаг «спорно» в UI.

### 6.3 Итеративный чат ревьюера с моделью

Чат привязан к `review_run_id`, агент с тулами:

| Тул | Что делает |
|---|---|
| `get_file(path, lines?)` | читает артефакт сдачи (после скраба) |
| `get_diff(path?)` | отдаёт diff |
| `get_criterion(id)` | текст критерия и якорей |
| `search_submission(query)` | поиск по работе |
| `propose_review_patch(criterion_id, score?, verdict?, feedback?)` | **предлагает** изменение черновика |

`propose_review_patch` ничего не меняет сам — рисует ревьюеру дифф черновика с
кнопками «Применить / Отклонить». Каждое применение пишется в `review_revisions`
с `author_type='ai_assisted'`.

## 7. AI-Detection

### 7.1 Принцип

Ансамбль сигналов разной природы, где два из четырёх не вероятностные. Детектор
получает тот же `SubmissionBundle`, что и ревью-агент.

```
   Bundle ──▶ 1. Форензика источника          вес 0.35 (детерминированно)
              git: 1 коммит на 800 строк, интервалы, порядок файлов;
              Docs: revision-всплески
              2. Перплексия (LOCAL)           вес 0.25
              logprobs малой модели, burstiness по окнам
              3. Стилометрия / эвристики      вес 0.15
              плотность комментариев, «идеальность», клише, отсутствие TODO
              4. LLM-judge со спанами         вес 0.25
              обязан вернуть цитаты
                      ▼
        Калибровка → score 0..1 + доверительный интервал + спаны с обоснованием
```

### 7.2 Почему форензика — главный вес

Признаки, которые почти не подделываются случайно: вся работа одним коммитом
«init», 900 строк за 4 минуты, коммиты каждые 20 секунд, файлы в порядке,
обратном зависимостям; ревизия на 4200 символов при среднем размере 80 (Docs).
Дёшево, детерминированно и объяснимо словами — важнее чистой точности, раз
сигнал по ТЗ не доказательство и на балл не влияет.

### 7.3 Перплексия локально

Малая модель (Qwen2.5-0.5B / rugpt3-small) на vLLM с `logprobs=1`, окна по 256
токенов со сдвигом 128: средняя NLL и burstiness (дисперсия NLL между окнами) —
человеческий текст «рваный», сгенерированный ровный. Обязана быть локальной:
нужны logprobs, которых внешние провайдеры почти не отдают, и объём токенов
большой.

### 7.4 Вывод в UI

```json
{
  "overall_score": 0.71,
  "confidence_band": [0.58, 0.83],
  "verdict_label": "средняя вероятность",
  "limitations": "Короткие фрагменты (<200 символов) не оцениваются. Шаблонный код из методички исключён.",
  "spans": [
    { "artifact": "README.md", "start": 1204, "end": 1890,
      "signals": ["low_perplexity", "llm_judge"], "score": 0.86,
      "reason": "Равномерно низкая перплексия + обороты «Важно отметить, что»" },
    { "artifact": "internal/service/order.go", "start": 0, "end": 640,
      "signals": ["git_forensics"], "score": 0.79,
      "reason": "Файл 640 строк добавлен одним коммитом за 3 минуты" }
  ]
}
```

**Анти-фактор:** шаблонный и сгенерированный фреймворком код (`go.sum`, миграции,
`*_pb.go`, boilerplate методички, `mlruns/`) исключается по allowlist — иначе
детектор ловит самого себя.

### 7.5 Политика курса по ИИ не бинарная

Условие `product_fraud`: «**необоснованное** использование ИИ-инструментов будет
считаться нарушением… **Если вы использовали ИИ — укажите это в работе и
опишите, как именно**».

Следствия для дизайна: запрещено не использование, а несогласованное; история
изменений — требование самого курса; вес сигнала зависит от критерия
(`ai_sensitive: true`) — сгенерированный `docker-compose.yaml` и сгенерированная
карта рисков разные события.

Вывод детектора — не «сгенерировано / нет», а матрица:

| | Сигнал есть | Сигнала нет |
|---|---|---|
| **Студент заявил ИИ** | Показываем заявление и сигнал рядом: совпадает ли описанное с найденным | Норма |
| **Студент не заявил** | **Главный случай** | Норма |

Отсюда дешёвый детерминированный шаг — поиск блока-декларации об ИИ в работе;
его текст выводится рядом со спанами, и «подозрение» превращается в проверяемое
расхождение между заявленным и найденным.

Клик по спану подсвечивает фрагмент слева; «Подтвердить» / «Отклонить» пишут
решение ревьюера в БД — это же датасет для калибровки порогов.

## 8. LLM-слой: PrivacyGateway и роутинг

### 8.1 Единая точка выхода

```python
class PrivacyGateway:
    async def complete(
        self,
        prompt: PromptSpec,
        *,
        task: TaskKind,               # REVIEW | DETECT | CHAT | NER | EMBED
        data_class: DataClass,        # PUBLIC | INTERNAL | CONTAINS_PD
        route_policy: RoutePolicy,    # LOCAL_ONLY | EXTERNAL_AFTER_SCRUB
    ) -> LLMResponse
```

Ни один сервис не импортирует SDK провайдера — только `PrivacyGateway`.
Проверяется тестом (`import openai` вне модуля gateway = fail). Это превращает
обещание не сливать ПДн в проверяемое утверждение.

### 8.2 Конвейер обезличивания

```
исходный текст
   ├─▶ 1. РЕГУЛЯРКИ: email, телефон, @telegram, паспорт, СНИЛС, ИНН,
   │     git author/committer, URL с ФИО, ссылки на профили
   ├─▶ 2. NER (ЛОКАЛЬНАЯ модель): Natasha/slovnet для русских ФИО, spaCy для латиницы
   ├─▶ 3. КОД-СПЕЦИФИКА: заголовки лицензий, .env, хардкод-креды, author-теги
   ├─▶ 4. ПСЕВДОНИМИЗАЦИЯ: Иван Петров → [PERSON_1], ivan@mail.ru → [EMAIL_1]
   │     map в Redis по request_id, TTL 1 час; стабильные токены сохраняют связность
   ├─▶ 5. ВАЛИДАТОР ОСТАТОЧНОГО РИСКА: повторный проход другим набором правил;
   │     нашли high-confidence ПДн → маршрут понижается до LOCAL_ONLY (fail-safe)
   ├─▶ 6. ВЫЗОВ ПРОВАЙДЕРА
   ├─▶ 7. РЕГИДРАТАЦИЯ: [PERSON_1] → Иван Петров, только внутри периметра
   └─▶ 8. АУДИТ: request_id, provider, model, route, data_class, redactions_count,
         prompt_sha256, tokens, cost, latency. Сырой промпт НЕ сохраняется
```

Псевдонимизация, а не вырезание: модель должна понимать, что «[PERSON_1] в
README ссылается на [PERSON_1] в коде», иначе качество ревью падает.

### 8.3 Матрица роутинга

| Задача | Маршрут | Модель (пример) | Почему |
|---|---|---|---|
| NER для ПДн | **LOCAL_ONLY** | slovnet / Natasha | Отправлять ПДн наружу, чтобы их найти, — абсурд |
| Перплексия | **LOCAL_ONLY** | Qwen2.5-0.5B (vLLM) | Нужны logprobs, огромный объём токенов |
| Эмбеддинги | **LOCAL_ONLY** | bge-m3 / e5-large | Объём: по сути весь корпус работ |
| Ревью по критериям | EXTERNAL_AFTER_SCRUB | claude-sonnet / gpt-4o-mini | Качество рассуждений критично для доверия |
| LLM-judge ГенИИ | EXTERNAL_AFTER_SCRUB | gpt-4o-mini | Дёшево, нужна классификация со спанами |
| Чат ревьюера | EXTERNAL_AFTER_SCRUB | claude-sonnet | Качество диалога |
| ToV-фидбек | EXTERNAL_AFTER_SCRUB | gpt-4o-mini | Стилистика, дёшево |

Оба маршрута — OpenAI-совместимый клиент, отличаются `base_url` и ключом.
Переключение — одна строка в конфиге; отсюда же режим «полностью локально, без
единого внешнего запроса».

### 8.4 Экономика прогона

Ориентир — < 5–10 ₽ за работу.

| Тип работы | Токенов после нормализации | Ревью | Judge | Итого |
|---|---|---|---|---|
| GO, этап 1–3 | ~7k | ~1 ₽ | ~0.4 ₽ | **~1.5 ₽** |
| System design, лаба | ~5k | ~0.8 ₽ | ~0.3 ₽ | **~1.1 ₽** |
| Продуктовое ДЗ (docx + xlsx) | ~8k | ~1.2 ₽ | ~0.4 ₽ | **~1.6 ₽** |
| tech_QA (21 тест-кейс) | ~6k | ~1 ₽ | ~0.3 ₽ | **~1.3 ₽** |
| Курс LLM **без** стриппинга ноутбука | ~116k | ~15 ₽ | ~6 ₽ | **~21 ₽** ⚠ |
| Курс LLM **со** стриппингом | ~14k | ~2 ₽ | ~0.7 ₽ | **~2.7 ₽** |

Перплексия и эмбеддинги локальные — ноль. Профили работы и ревьюера (§9.2) —
ещё ~0.2 ₽ на сдачу.

**Бюджет ломает не сложность разбора, а неотфильтрованный мусор**: одна работа с
сырым `.ipynb` стоит как четырнадцать нормальных. Остальные механики удержания
цены: prompt caching рубрики и условия, батчинг критериев по 3–5, Format Gate до
модели, лимит на размер диффа с деградацией до ревью по ключевым файлам.

## 9. Assignment Engine

### 9.1 Два разных вопроса

| Вопрос | Кто отвечает | Почему |
|---|---|---|
| Что это за работа и что за ревьюер? | LLM и эмбеддинги | Требует понимания содержания: темы, стек, сложность |
| Кому конкретно её отдать? | Детерминированный солвер | Воспроизводимость, объяснимость, пересчёт при болезни ревьюера |

LLM работает вне горячего пути: строит признаки один раз на сдачу и периодически
на ревьюера. Координатор должен уметь ответить студенту «почему тебя проверяет
именно он».

### 9.2 Профили

`WorkProfile` (1 вызов на сдачу, ~1k токенов): `topics`, `stack`, `complexity`
(0..1), `risk_criteria`, `special_needs`, `est_review_minutes` — прогноз
трудоёмкости, а не «одна работа = один слот». Работа по GO на 6k токенов и
работа с ноутбуком на 116k — это 20 минут и полтора часа, а не «две работы».

`ReviewerProfile` (пересчёт раз в сутки по истории ревью): `strength_vector`,
`weak_topics`, `tov`, `median_minutes_per_work` (фактическая скорость),
`onboarding`.

`StudentProfile`: `recurring_errors`, `last_reviewer_id`, `growth_area`.

### 9.3 Решение принимает солвер

```python
def match_score(r: ReviewerProfile, w: WorkProfile, s: StudentProfile) -> float:
    if r.minutes_committed + w.est_review_minutes > r.week_capacity_minutes: return -inf
    if conflict_of_interest(r, w): return -inf          # соавтор коммитов
    return (
        + 1.0 * cosine(r.strength_vector, w.topic_vector)
        + 0.6 * covers(r.skills, w.special_needs)
        + 0.4 * continuity(r, s.last_reviewer_id)
        + 0.3 * tov_fit(r.tov, s.growth_area)
        - 0.8 * load_ratio(r)
        - 0.5 * deadline_risk(r, w)
        + 0.2 * fairness_bonus(r)
        - 0.7 * onboarding_penalty(r, w.complexity)
    )
```

- **Batch (основной).** В материалах курса: «проверка начинается после окончания
  дедлайна и занимает не более 7 дней» — значит распределяется весь поток разом.
  Задача о назначениях: венгерский алгоритм или min-cost flow по матрице
  `match_score`, глобальный оптимум вместо жадного разбора.
- **Online.** Для rolling-дедлайнов: тот же скор, жадный выбор, периодическая
  ребалансировка.

### 9.4 Где LLM заходит в решение

Одно место, в советующей роли: предложение переназначить работу, помеченную
пограничной (низкая уверенность или разброс между прогонами). Кнопка «Применить»
— за человеком.

### 9.5 Что осталось детерминированным намеренно

Расписание не должно менять ответ между запусками: координатор, видящий в 10:00 и
10:05 разные распределения одного пула, перестаёт пользоваться системой. Профили
кэшируются и версионируются, солвер получает их как данные, каждое назначение
хранит `explain` — вклад каждого слагаемого.

## 10. Схема данных (PostgreSQL)

```
courses ──< assignments ──< rubrics ──< rubric_criteria
                │
                └──< submissions ──< submission_artifacts
                        │            └ (path, kind, content_ref, lang, size)
                        ├──< submission_history_events
                        │       (commit/revision: ts, author_hash, added, removed)
                        ├──< review_runs ──< review_criterion_results ──< evidence_citations
                        │       ├──< review_chat_messages  (role, content, tool_calls)
                        │       └──< review_revisions      (author_type, diff, ts)
                        ├──< ai_detection_runs ──< ai_detection_spans
                        │                              └ (artifact, start, end, signals[],
                        │                                 score, reason, reviewer_verdict)
                        └──< review_final  (score, feedback, approved_by, approved_at)

format_gate_results (submission_id, check_id, status, expected, actual, blocking)
work_profiles     (submission_id, topics[], stack[], complexity,
                   est_review_minutes, risk_criteria[], topic_vector)
reviewer_profiles (reviewer_id, strength_vector, weak_topics[], tov,
                   median_minutes_per_work, onboarding, computed_at)
assignment_explain (submission_id, reviewer_id, term, contribution)

students (внутр. id, внешние handle'ы, БЕЗ лишних ПДн)
reviewers (capacity_minutes, max_wip, skills[])
assignments_queue (submission_id, reviewer_id, assigned_at, due_at, state)
llm_call_audit (request_id, provider, model, route, data_class,
                redactions, prompt_sha256, tokens_in/out, cost, latency)
sheets_sync_log (submission_id, row, synced_at, status)
submission_embeddings (vector) ← pgvector, для дубликатов
```

Состояния сдачи:

```
received → normalized → scrubbed → analyzing → draft_ready
   → in_review → (needs_changes ⇄ in_review) → approved → exported
                                   ↘ failed → manual_fallback
```

`manual_fallback` обязателен: если LLM недоступен, ревьюер получает работу с
пустым черновиком и всё равно может её проверить. Система не должна быть единой
точкой отказа процесса.

## 12. Фронтенд: экраны

**Review Workspace** — главный экран. Работа слева (файлы, дифф, подсветка

время, ребалансировка), **редактор рубрики** (JSON-форма с превью промпта),
**аудит** (журнал обращений к LLM).

## 13. Безопасность и ответственность

| Риск | Митигация |
|---|---|
| Утечка ПДн во внешний API | `PrivacyGateway` как единственный выход + CI-правило + fail-safe валидатор остаточного риска + `LOCAL_ONLY` для чувствительных задач |
| Галлюцинации в оценке | Обязательные цитаты с программной валидацией; балл считает код; флаг «спорно»; ревьюер утверждает |
| Ложное обвинение в ГенИИ | Advisory-статус, доверительный интервал, описание ограничений, allowlist шаблонного кода, кнопка «Отклонить», нулевое влияние на балл |
| Недоверие ревьюеров | Цепочка рассуждений и цитаты, спор с моделью в чате, полный лог правок |
| Отказ LLM-провайдера | `manual_fallback`, ретраи с бэкоффом, автопереключение external → local |
| Prompt injection из работы | Контент студента в отдельном блоке с инструкцией игнорировать директивы внутри; вывод валидируется схемой; тулы read-only |
| Несанкционированный доступ | RBAC + скоуп по курсу/назначению |
| Подмена вебхука | HMAC-подпись GitHub, дедуп по delivery_id |
| Аудируемость оценки | `review_revisions`: кто, когда, что изменил, ai / human / ai-assisted |

Сырые промпты не хранятся — только SHA-256 и счётчики. PII-map живёт в Redis с
TTL и не попадает в долговременное хранилище.

## 14. Метрики эффекта

| Метрика | Как считаем | Цель |
|---|---|---|
| Время на одну проверку | `approved_at − first_opened_at` | 30 мин → 10–15 мин |
| Доля принятых без правок | пустые `review_revisions` / всего | > 40% |
| Дельта балла AI vs финал | `avg abs(ai_score − final_score)` | < 8 из 100 |
| Ручных действий на работу | счётчик в UI | −70% |
| Просроченные проверки | статусы очереди | −50% |
| Время координатора | опрос + число ручных переназначений | 10 ч/нед → 1–2 ч/нед |
| Стоимость прогона | `llm_call_audit.cost` | < 5–10 ₽ |
| Precision детектора ГенИИ | подтверждённые / всего сигналов | > 0.7 |
| CSI студента | опрос по фидбеку | не ниже базового |

Дельта `ai_score` vs `final_score` — источник данных для дообучения промптов.

уровня решений уже разложены по папкам.

**Вторым — system_design, лаба 1.** Markdown в том же GitHub, новый канал не
нужен, зато другой тип работы: текстовый документ с диаграммами, дробные баллы,
порог зачёта, готовые проверочные пункты.

**Третьим — tech_QA.** Таблица вместо документа; Format Gate нагляден: «21
тест-кейс требуется, 18 найдено» без единого токена.

Продуктовые направления — на «масштабирование»: там `.docx`/`.xlsx` и отдельные
парсеры.

### Что режем

- Аутентификация — один хардкод-логин на роль, не OAuth.
- Векторный поиск дубликатов — COULD.
- Google Docs и Stepik — не делаем, заглушек в коде нет.
- Мультиязычность UI, мобильная вёрстка, тонкие настройки прав.
- Реальный вебхук — poller надёжнее на демо.

### Что нельзя резать

Обязательные функции ТЗ (распределение, ревью по критериям, детектор ГенИИ),
**валидация цитат**, **PrivacyGateway**, **панель ГенИИ со спанами** и **Format
Gate** — то, чем решение отличается от обёртки над ChatGPT.

## 16. Покрытие требований ТЗ

**MUST:**

| Требование | Где закрыто |
|---|---|
| Распределение ДЗ по нагрузке | §9 |
| Предварительное ревью по критериям + рекомендации | §6, §12 |
| Выявление ГенИИ с уверенностью и основаниями | §7 |
| Интерфейс ревьюера: посмотреть/утвердить/изменить | §12 |
| Модуль анонимизации ПДн | §8.2 |

**Дополнительные (нужно ≥3, у нас 4):** штраф за просрочку по правилу рубрики;
автоперенос итогов в Google Sheets; персонализированный ToV-фидбек; дашборд
аналитики. В резерве — детекция дубликатов через pgvector.

**Ограничения ТЗ:** AI не заменяет ревьюера (утверждение обязательно, балл не
проставляется автоматически); стоимость обоснована (§8.4); ПДн не уходят в
незащищённые сервисы (§8.2, §13); только реально существующие сервисы; сигнал
ГенИИ рекомендательный.

## 17. Масштабирование за пределы MVP

| Направление | Что делаем |
|---|---|
| Новый канал сдачи | Новая реализация `ProviderInput`, остальная система не меняется |
| Новый курс | Новый JSON рубрики, кода не пишем |
| Рост нагрузки | arq-воркеры горизонтально; перплексия на отдельном GPU-пуле |
| Полный отказ от внешних API | `route_policy=LOCAL_ONLY` глобально |
| Мультитенантность | Скоуп по `organization_id` в RBAC, партиционирование |
| Обучение на своих данных | `review_revisions` + вердикты по спанам — размеченный датасет |

## 18. Открытые вопросы к организаторам

Закрыто репозиторием примеров: правила штрафа за просрочку (досдача в течение
1 дня — минус 1 балл, позже 0); доступность истории ревизий Google Docs (курс сам
её требует); форма критериев (четыре разных, §6.0).

Осталось:

1. Работы приходят как PR в живом репозитории или как выгрузки вроде
   `course-go-avito-<username>-<sha>`? Если второе — ingestion идёт через
   Classroom API, а не через вебхуки PR.
2. Есть ли эталонная разметка — баллы по критериям и текст фидбека от реального
   ревьюера? Без неё нечем измерить расхождение `ai_score` и `final_score`.
3. Как читать ярлыки в примерах: «слабое» — конкретный балл или диапазон?
4. Ограничения безопасности Авито на внешних LLM-провайдеров: допустим ли
   OpenRouter или нужен полностью локальный контур?
5. Кто заводит рубрику в проде: методист через Rubric Compiler на каждое задание
   или условия достаточно единообразны для пакетной компиляции?
