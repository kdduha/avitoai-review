# Фронтенд: состояние и как его воспроизвести

Документ для того, кто берёт работу дальше. Парный к `handover-backend.md`:
отвечает на те же три вопроса — что работает, как это запустить и на чём здесь
спотыкаются.

Рабочее место ревьюера образовательных программ Авито: React + Vite + TypeScript,
TanStack Query, Tailwind v4, Recharts.

```bash
npm install
npm run dev        # http://localhost:5173
npm run build
npm run typecheck
npm run gen:api    # типы из OpenAPI поднятого бэкенда
npm run e2e        # Playwright: сам поднимает и фронт, и бэкенд
```

Бэкенд нужен для проверки работ; ведомость и дашборд открываются и без него.

```bash
cd ../backend && uv run uvicorn avito_reviewer.app.main:app --port 8000
```

`/api` проксируется на `http://localhost:8000` (`vite.config.ts`), переопределяется
переменной `VITE_API_BASE`.

## Что здесь есть

| Маршрут | Экран | Данные |
|---|---|---|
| `/check` | запуск проверки по ссылке | живой API |
| `/review/:id` | Review Workspace: правка балла, вердикт по спану, утверждение, чат с моделью | живой API (демо — офлайн) |
| `/rubrics` | против чего ставится вердикт; для руководителя — ещё и сборка новой из условия | живой API |
| `/queue` | своя очередь (руководитель — весь поток, `?all=true`) | живой API |
| `/streams` | потоки: сдачи, очередь, просрочка, баллы, нагрузка; руководителю — назначение ревьюеров и раскладка | живой API |
| `/assignments` | какая рубрика выдана какому потоку и до какого числа | живой API |
| `/my-work` | кабинет студента: что сдавать, что сдано, что получено | живой API |
| `/courses/:id` | ведомость, дашборд, ревьюеры потока | синтетика |
| `/students/:id` | карточка студента | синтетика |
| `/curators` | кто на каких потоках | синтетика |

Ролей четыре, и называются они **как на сервере**: `student`, `reviewer`,
`methodist`, `admin`. Свой словарь фронта («curator» / «head») разъезжался с
сервером молча — токен приходил с ролью `admin`, а интерфейс переводил её в
`head` и обратно на каждом входе. Русские подписи живут в `RoleSwitch`.

Роль переключается в шапке и лежит в `localStorage`; при каждом переключении
`app/session.tsx` логинится в одноимённый сеяный аккаунт (пароль
`VITE_BACKEND_PASSWORD`/`avito2026`) и держит токен в `lib/backend.ts`.
Сохранённая роль проверяется на существование: словарь уже менялся, и
`localStorage` переживает обновление интерфейса — неизвестное значение
откатывается к `reviewer`, иначе вход молча не проходит и все запросы уходят
без токена. Настоящий вход тоже есть — кнопка «Войти» (`LoginModal.tsx`)
пускает под аккаунтом, заведённым через `POST /users`.

`lib/types.ts::atLeast` повторяет серверную лестницу прав, но решает только,
**что показать**; что разрешить, решает сервер, и 403 он вернёт независимо от
этого файла.

**Review Workspace — две колонки, а не три.** Слева работа, справа одно окно с
вкладками «Черновик оценки» и «Признаки ГенИИ». Панель детектора занимала треть
ширины и почти всегда была пуста, а разбор из-за неё читался в две трети
строки. Над списком критериев закреплена ровно одна строка — формальные
проверки; отзыв, «требуют внимания» и объяснение итога живут внутри прокрутки и
уезжают по мере чтения. Это не вкусовое: три закреплённых блока подряд
оставляли списку критериев одну строку.

## Граница живого и синтетики

Бэкенд больше не без состояния: `POST /review` сохраняет `Submission` в
Postgres, и `submission_id` из его ответа — рабочий ключ дальше. Правка балла
(`PATCH /submissions/{id}/review`) и вердикт по спану детектора
(`POST /submissions/{id}/ai-detection/{span_id}/verdict`) на живом прогоне
уходят на сервер и возвращают то, что он на самом деле посчитал и сохранил —
`lib/runs.ts`'s `setScore`/`setSpanVerdict` асинхронны именно поэтому.
`submissionId === null` (демо-прогоны, записанные в `mocks/`) — сигнал, что
PATCH'ить нечего, и правка остаётся локальной прикидкой с пометкой `edited`.

Курсов, потоков и ведомости в Postgres по-прежнему нет: сущностей курса и
потока в схеме не существует. Само распределение на бэкенде уже есть —
`POST /distribute` раскладывает пакет сдач по ревьюерам и объясняет каждое
назначение, — но экрана под него во фронте пока нет (см.
`docs/handover-backend.md`). Очередь
(`/me/queue`) уже настоящая: `/queue` — реальный список сдач, не синтетика.
Граница «живое / синтетика» держится на первом, а не на состоянии вообще:

**Живое** — `GET /init`, `GET /rubrics`, `GET /rubrics/{id}`,
`POST /rubrics/compile`, `POST /rubrics`, `GET /cost`, `POST /review`,
`POST /detect`, и всё под `/submissions/*` и `/me/queue` (`/queue` и Review
Workspace читают их напрямую; `/courses/*` — в синтетике). Открытие сдачи не
из этой вкладки (по ссылке `/review/{id}` или из очереди) идёт через
`GET /submissions/{id}` (`lib/runs.ts:loadSubmission` →
`lib/workspace.ts:buildWorkspaceFromDetail`) — используется снимок рубрики
из ответа (`SubmissionDetail.rubric`), а не текущий каталог: если методист
успел поправить JSON, старые сдачи не пересчитываются по другим весам молча.
Клиент — `src/lib/backend.ts`; каждый запрос несёт `Authorization: Bearer
<token>` из `app/session.tsx` (см. выше).

**Синтетика** — курсы, потоки, студенты, ведомость, ревьюеры. Вся за
`src/lib/api.ts`, форма функций — та, что появится в REST.

`src/mocks/` импортируют ровно два файла: `lib/api.ts` (каталог) и `lib/runs.ts`
(записанные прогоны). Компоненты ходят только через запросы. **Если понадобится
импортировать что-то из `mocks/` в компонент — это сигнал, что абстракция
протекла**; в прошлый раз такая протечка стоила отдельного рефакторинга.

Мок-экраны помечены плашкой `MockNotice`: на демо должно быть видно, где работает
настоящий разбор, а где нарисованы данные.

## Данные

### Программы

`src/mocks/programs.ts` — каталог по материалам организаторов (репозиторий
`ai-talent-hub-avito/homework_examples`), а не выдуманный. Из девяти направлений
оставлены пять — те, у которых есть записанный разбор: открыть курс и не суметь
провалиться внутрь задания хуже, чем не показать курс вовсе. Заодно они
покрывают разнообразие: шесть каналов сдачи, три шкалы (6, 10 и 20 баллов),
от одного задания до трёх.

Что взято из условий и легко потерять при правках:

- **шкалы разные**, и на Go баллов в условии нет вовсе — их задаёт методист.
  Поэтому распределения на дашборде считаются в долях от максимума;
- **досдача** в grace-окно стоит балл за день, позже работа оценивается в ноль;
- **проверка идёт волной**: «начинается после окончания дедлайна и занимает не
  более 7 дней». Отсюда всплеск на графике по неделям, а не ровный поток;
- **строка ведомости** повторяет таблицу организаторов: сумма за ДЗ,
  посещаемость, вовлечённость, экзамен, итог и оценка, где
  `итог = сумма × 0.5 + экзамен × 0.4 + вовлечённость / 10`;
- **идентификаторы студентов** обезличены шестизначным числом — как в настоящей
  ведомости.

Данные детерминированы: два открытия страницы дают одну и ту же ведомость.

### Записанные прогоны

| Прогон | Работа | Зачем он нужен |
|---|---|---|
| `demo` | сервис на Go, pull request | провал дословного формального требования |
| `demo-sysdesign` | Markdown с диаграммой C4 | шкала 6 с дробными критериями, работа ровно на пороге, две проверки гейта без ответа |
| `demo-backend` | FastAPI и тесты | градация 0.5 из условия, штраф за просрочку уводит 6.5 под порог |

Прогоны лежат **в формате ответов бэкенда** (`ReviewResponse` / `DetectResponse`)
и проходят через тот же адаптер `lib/workspace.ts`, что живой прогон. Это
сделано намеренно: своя форма у демо означала бы, что расхождение с сервером
всплывёт только на живом ключе.

Разбор доступен там, где есть рубрика, — сейчас у трёх программ из пяти. У
остальных ячейка ведомости не ссылка: показывать разбор работы по Tech QA против
рубрики по Go хуже, чем не показывать ничего.

## Грабли: что диктует бэкенд

Правила, которые ломаются молча, если о них не знать:

- **название, максимум, вес и проверочные пункты критерия лежат в рубрике** —
  вердикт знает только `criterion_id`. Панель соединяет их сама;
- **`line_numbers`, а не `first_line + index`.** У фрагмента из диффа номера
  строк идут с пропусками (1–4, затем 119–122). Нумерация по позиции уводит
  цитату на чужую строку — на `partial`-файлах это выглядит правдоподобно и
  потому особенно опасно;
- **`partial`** значит, что модель видела не весь файл, и вывод «этого в работе
  нет» здесь ненадёжен;
- **Format Gate возвращает разбор проверок**, и у проверки есть третье
  состояние — `inconclusive`: ответить по доступным данным нельзя. Это не
  провал;
- **гейт больше не останавливает разбор.** Статуса `blocked` нет: непройденная
  проверка уровня `blocking` выводится заметной строкой, но модель отрабатывает,
  и балл по критериям это учитывает
- **недоступный сигнал детектора — не ноль, а «не смотрели»**;
- **итог считает агрегатор**: веса, шаг шкалы, обязательные минимумы и штраф за
  просрочку, причём два последних могут обнулить работу целиком. На живом
  прогоне правка балла уходит на `PATCH /submissions/{id}/review` и получает
  обратно настоящий пересчитанный итог; предварительная сумма по критериям
  (`edited`, без пересчёта) осталась только на демо-прогонах, где сервера для
  PATCH нет.

Типы генерируются из OpenAPI (`npm run gen:api`), руками `backend.d.ts` не
правят. Так и обнаружилось появление `student_name` в API.

**nginx во `frontend`-контейнере по умолчанию рвёт `/review` на реальном
ключе.** Дефолтный `proxy_read_timeout` — 60s; настоящий разбор с несколькими
батчами критериев и детектором на внешней модели легко занимает больше
(зафиксировано — 4 минуты 9 секунд на реальном PR). Без ключа (`fake`) этого
не видно — весь путь укладывается в секунды. `frontend/nginx.conf` держит
`proxy_read_timeout 300s` (и `send`/`connect` тоже) именно поэтому — не
трогайте вниз без причины.

## Как добавить

**Программу в каталог** — запись в `PROGRAMS` (`src/mocks/programs.ts`). Ведомость,
дашборд, потоки и студенты соберутся сами.

**Рубрику** — JSON в `backend/rubrics/`. Каталог и экран `/rubrics` подхватят её
без правок фронта. Шкала, критерии и Format Gate берутся из условия задания;
сумма максимумов критериев должна сходиться с `scale.total_max`.

**Записанный прогон** — файл рядом с `src/mocks/demoBackend.ts`: снимок рубрики в
`src/mocks/rubric.ts`, файлы работы, черновик и отчёт детектора в формате
ответов бэкенда. Дальше зарегистрировать в `src/lib/runs.ts` и добавить в
`DEMO_BY_COURSE` и `DEMO_BY_RUBRIC`. Цитаты не проставляют руками — их ищет
`locator()` по тексту файла, как это делает настоящий валидатор.

## Что сделано с прошлой ревизии этого документа

1. **Аутентификация подключена.** `app/session.tsx` логинится в сеяный
   аккаунт при старте и при смене роли; `lib/backend.ts` держит токен в
   памяти и прикладывает его ко всем запросам. Без этого ни один живой вызов
   не работал бы вовсе — бэкенд стал требовать Bearer-токен раньше, чем фронт
   узнал об этом.
2. **Экран сборки рубрики есть** (`features/rubrics/CompileRubricPanel.tsx`,
   доступен руководителю с `/rubrics`). Условие → черновик → подтверждение;
   `warnings` и `open_questions` показаны отдельным блоком над критериями, а у
   каждого критерия — своя пометка «дословная цитата / пересказ / источник не
   найден» рядом с ним самим, не общим числом сверху.
3. **Двойной ingest закрыт.** `startRun` (`lib/runs.ts`) зовёт `/review` один
   раз, с `with_detection`; детектор и ревью теперь гарантированно смотрят на
   одну и ту же ревизию PR.
4. **Правка балла и вердикт по спану персистентны на живом прогоне.**
   `PATCH /submissions/{id}/review` и `POST .../ai-detection/{span_id}/verdict`
   — сервер пересчитывает итог и возвращает его; демо-прогоны (`submissionId:
   null`) по-прежнему считают локально и помечают правку как предварительную.
   Утверждение (`POST .../review/approve`) тоже уходит на сервер.
5. **Playwright есть** (`e2e/`, `npm run e2e`): обход маршрутов без ошибок
   консоли и горизонтального скролла на обеих ролях, правка балла, переход по
   цитате, вход и переключение роли, сборка рубрики.
   Конфиг сам поднимает и фронт, и бэкенд (`playwright.config.ts`).
6. **Чат с моделью подключён.** `ChatDock.tsx` на живом прогоне (`submissionId`
   есть) читает историю (`GET .../chat`) и ведёт ход через SSE
   (`POST .../chat`, `backend.ts:sendChat`) — сервер досчитывает весь ход и
   отдаёт его как последовательность `data:`-событий, не токен за токеном.
   Каждый шаг с `tool_name` подписан («читает файл», «смотрит дифф» и т. д.);
   шаг с `proposed_patch` получает кнопку «Применить», которая уходит в тот же
   `PATCH /submissions/{id}/review`, что и ручная правка балла, и обновляет
   черновик через `withPatchedDraft`. На демо-прогонах (`submissionId === null`)
   чат остаётся read-only записанной веткой — показывать придуманный ответ
   рядом с настоящим черновиком нельзя.
7. **`/queue` читает настоящий `GET /me/queue`** (`?all=true` для
   руководителя), а не `mocks/catalog.ts`. Каждая строка ведёт на
   `/review/{submission.id}` — реальный UUID сдачи, не записанный демо-прогон.
8. **Открытие сдачи не из этой вкладки работает.** `ReviewPage` больше не
   требует, чтобы прогон был запущен в этой же вкладке: если `id` в URL нет в
   локальном кэше, он подтягивается через `GET /submissions/{id}`
   (`lib/runs.ts:loadSubmission`) — так работает переход из очереди и прямая
   ссылка `/review/{submission_id}`.
9. **Настоящий вход есть.** Кнопка «Войти» в шапке (`LoginModal.tsx`) —
   логин/пароль напрямую в `POST /auth/login`, а не только два
   захардкоженных быстрых переключателя. Открывает доступ к аккаунтам,
   заведённым через `POST /users`.

## Что не сделано

1. **`/courses/*`, `/curators`, `/students/*` остаются синтетикой.** Сущности на
   бэкенде теперь есть, и статистика по ним считается по-настоящему — на
   `/streams`. Старый дашборд курса и ведомость по-прежнему живут на
   `mocks/catalog.ts`: перевести их значит потянуть за собой студентов,
   ведомость и формулу итога, и это отдельный заход.
2. **Кнопка «Открыть демо-прогон» подставляет чужой разбор.**
   `demoRunForRubric` (`lib/runs.ts`) при отсутствии записанного прогона
   возвращает прогон по Go. Выбрали рубрику по системному дизайну — получили
   разбор сервиса на Go: правдоподобно и неверно. Готовое решение лежит в ветке
   `frontend-wip-rescue`: функция возвращает `null`, и экран говорит, что
   разбора по этой рубрике нет.
3. **Идентификаторы в коде отстают от словаря.** `Curator`, `curatorId`,
   маршрут `/curators` — пользователю не видны, но расходятся с сервером, где
   везде `reviewer`. Механическая правка.
4. **Управление аккаунтами (`/users`) без своего экрана.** Заводить людей и
   менять роли можно через API/Swagger; `LoginModal` умеет только вход.
5. **Кабинет студента — только свои работы.** Сдача, список, оценки и отзыв
   есть; истории попыток по одному заданию, дедлайнов календарём и уведомлений
   нет.

## Визуальный язык

Метафора — не терминал, а разметка на полях: ревьюер читает работу и оставляет
пометки. Бумага `#fbfbfa` на поле `#f1f2f0`, графитовый текст, единственный
интерактивный цвет — чернильно-синий, подсветка цитаты — песочная полоса с
линейкой слева. Моноширинный шрифт только там, где действительно код или путь.

Одно громкое место на экран: в Review Workspace это итоговый балл, и кнопка
утверждения стоит рядом с числом, которое утверждает. Токены —
`src/styles/index.css`, палитра графиков проверена на различимость при
дальтонизме.
