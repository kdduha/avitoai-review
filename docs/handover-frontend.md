# Фронтенд: состояние и как его воспроизвести

Документ для того, кто берёт работу дальше. Парный к `handover-backend.md`:
отвечает на те же три вопроса — что работает, как это запустить и на чём здесь
спотыкаются.

Рабочее место куратора образовательных программ Авито: React + Vite + TypeScript,
TanStack Query, Tailwind v4, Recharts.

```bash
npm install
npm run dev        # http://localhost:5173
npm run build
npm run typecheck
npm test           # юнит-тесты (vitest)
npm run gen:api    # типы из OpenAPI поднятого бэкенда
```

Бэкенд нужен для проверки работ; ведомость и дашборд открываются и без него.

```bash
cd ../backend && uv run uvicorn avito_reviewer.app.main:app --port 8000
```

`/api` проксируется на `http://localhost:8000` (`vite.config.ts`), переопределяется
переменной `VITE_API_BASE`.

## Граница живого и синтетики

Бэкенд без состояния: он принимает ссылку на сдачу и отдаёт разбор, но нигде его
не хранит, и учебного каталога у него нет вовсе. Отсюда деление, и его важно не
размыть при доработках.

**Живое** — `GET /init`, `GET /rubrics`, `GET /rubrics/{id}`, `GET /cost`,
`POST /review`, `POST /detect`, `POST /rubrics/compile`, `POST /rubrics`. Всё это
в `src/lib/backend.ts`.

**Синтетика** — курсы, потоки, студенты, ведомость, кураторы. Вся за
`src/lib/api.ts`, форма функций — та, что появится в REST.

Слово «синтетика» здесь значит «нет ручки, поэтому данные лежат у нас», а не
«числа выдуманы». Каталог, шкалы, дедлайны и правила досдачи взяты из условий
организаторов; ведомость построена вокруг девяти настоящих строк их
Google-таблицы. Достроено то, чего в материалах нет физически: имена, размеры
восьми групп из одиннадцати и распределение баллов по студентам. Граница между
взятым и достроенным проходит по коду и подписана — `cohortIsReal` у программы,
`null` вместо непроставленного порога, комментарий «ОЦЕНКА» у рядов дашборда,
которые нечем посчитать.

`src/mocks/` импортируют ровно два файла: `lib/api.ts` (каталог) и `lib/runs.ts`
(записанные прогоны). Компоненты ходят только через запросы. **Если понадобится
импортировать что-то из `mocks/` в компонент — это сигнал, что абстракция
протекла**; в прошлый раз такая протечка стоила отдельного рефакторинга.

Мок-экраны помечены плашкой `MockNotice`: на демо должно быть видно, где работает
настоящий разбор, а где нарисованы данные.

## Данные

### Программы

`src/mocks/programs.ts` — каталог по материалам организаторов (репозиторий
`ai-talent-hub-avito/homework_examples`), а не выдуманный. Здесь **все
одиннадцать направлений**: директорий в репозитории девять, но `data_science/`
— это четыре разных курса (MLSD, LLM, основы backend, GPU). Домашних работ
двадцать, а заданий двадцать два: единственная работа по Go состоит из трёх
этапов, которые сдаются и проверяются по отдельности.

Главное правило каталога: **чего в материалах нет — того нет и здесь.**

- **порог зачёта** назван только у системного дизайна (4 из 6 и 6 из 10). У
  остальных двадцати заданий `passThreshold: null`, и балл в ведомости не
  красится. Проставить всем «60% от максимума» значило бы выдумать правило
  за методиста;
- **дробный шаг** назван только у системного дизайна и у основ backend
  («0.5 балла — тесты запускаются, но не все проходят»). У остальных шаг 1;
- **дедлайны и правила досдачи** есть только у продуктовых направлений
  (`product`, `business-models`, `fraud`) — конкретные даты из условий. У
  восьми курсов из одиннадцати сроков в материалах нет вовсе, поэтому
  `deadline: null`, и **просрочек у них не бывает**: `overdue` там ноль. Это
  следствие честных данных, а не поломка дашборда. Прежняя раскладка «по 14
  дней от 1 сентября» была выдумкой и удалена;
- **на Go шкалы нет в условии вообще.** Максимум 10 взят из скомпилированной
  рубрики `go-task1` и подписан как таковой;
- **блок «Работа с ИИ-инструментами»** есть ровно у четырёх заданий: product
  ДЗ №1 и ДЗ №4, `fraud`, `business-models`. Только у них `declareAi: true`;
- **размеры групп** настоящие у трёх курсов — из счётчика Stepik «верно
  решили N учащихся»: Tech QA 49, бизнес-модели 38, антифрод 22. Остальные
  оценочные, и это машиночитаемо: `cohortIsReal: false`.

Нумерация заданий в `product` — настоящая (ДЗ №1…№5), а не по именам
директорий репозитория: там `Пример ДЗ 1` — это на самом деле ДЗ №5.

### Ведомость

Ведомость лежит **файлом**, а не рождается из генератора на импорте:
`src/mocks/data/roster.ts` (данные), `src/mocks/ledger.ts` (формула, шкала
оценок и девять настоящих строк), `frontend/scripts/build-roster.mjs`
(сборщик, `npm run roster` и `npm run roster:check`).

Раньше числа были воспроизводимы, но невидимы: чтобы узнать, что в ведомости,
надо было исполнить `rng()` в голове. Теперь её можно открыть и прочитать, а
скрипт остаётся рядом и объясняет, откуда что взялось.

Источник — `workflow/фиксация результатов.png` из репозитория организаторов:
скриншот той самой Google-таблицы, куда ревьюер переносит результат.
**Девять её строк лежат в потоке `qa-a` дословно** — id, сумма, посещаемость,
вовлечённость, экзамен, «Количество дз» вместе с настоящей опечаткой «ю»
вместо числа, и «Согласие на оценку» пятью разными написаниями.

Что проверено арифметикой на всех девяти строках:

- `итог = сумма × 0.5 + экзамен × 0.4 + вовлечённость / 10`. Посещаемость в
  формулу не входит — это отдельная колонка;
- вовлечённость принимает ровно три значения: 0, 10, 20; экзамен 30 — это
  потолок, а не середина;
- **оценка выводится из итога таблицей абсолютных порогов**:
  `≥45 → 10`, `≥43 → 9`, `≥42 → 8`, `≥41 → 7`, `≥39 → 6`, `≥30 → 5`, иначе 4.
  Прежние пороги в долях от максимума (`0.9 → 10`, `0.83 → 9`, …) ошибались на
  **пяти строках из девяти**. `npm run roster:check` печатает обе колонки
  рядом — это и есть доказательство.

Итог и оценка **не хранятся, а считаются**: так девять настоящих строк
воспроизводятся, а не переписываются.

Один шов оставлен сознательно и подписан в коде: «Итоговая сумма» ведётся на
шкале организаторов (курс из девяти ДЗ, максимум 90) и **не равна сумме ячеек**
таблицы — у наших программ от одного до пяти заданий, и при сумме по ним никто
не дотянулся бы до порога «≥45 → 10», вся ведомость была бы из пятёрок. Связь
не потеряна: из ведомости берётся доля `homework / 90`, и по ней раздаются
баллы за конкретные задания — ячейка и строка говорят про одного студента одно
и то же.

Данные детерминированы: два открытия страницы дают одну и ту же ведомость, а
повторный запуск сборщика — побайтово тот же файл.

### Записанные прогоны

| Прогон | Работа | Зачем он нужен |
|---|---|---|
| `demo` | сервис на Go, pull request | провал дословного формального требования |
| `demo-sysdesign` | Markdown с диаграммой C4 | шкала 6 с дробными критериями; работа набирает **ровно порог и всё равно не зачтена** — провален обязательный минимум |
| `demo-backend` | FastAPI и тесты | градация 0.5 из условия, штраф за просрочку уводит 6.5 под порог |
| `demo-qa` | **настоящая** таблица тест-кейсов Tech QA | шкала на **20 баллов**; **порога зачёта нет вовсе**; гейт целиком из «?» — четыре формальных правила не имеют обработчика для git-канала |
| `demo-fraud` | **настоящая** карта рисков продукта | необъявленный ИИ: `mismatch` при `declared_ai_usage: false`; `partial` из-за внешней таблицы; два сигнала из четырёх |
| `demo-go-weak` | **настоящий** слабый репозиторий на Go | 7 из 10 при пороге 6 — **и незачёт**: провал обязательного минимума не компенсируется суммой. Файл с разрывом нумерации строк |

Три последних собраны из настоящих студенческих работ репозитория
организаторов — код, таблица и документ взяты без правок.

Прогоны лежат **в формате ответов бэкенда** (`ReviewResponse` / `DetectResponse`)
и проходят через тот же адаптер `lib/workspace.ts`, что живой прогон. Это
сделано намеренно: своя форма у демо означала бы, что расхождение с сервером
всплывёт только на живом ключе.

Что это ловит, проверяет `frontend/scripts/check-demo-runs.ts` — по всем шести
прогонам сразу: цитата дословно совпадает со строкой файла, `criterion_id` есть
в снимке рубрики, `line_numbers` длиной в число строк, `evidence_coverage`
сходится с фактическим, спаны и `locations` гейта ссылаются на существующие
строки, и **`passed` не спорит с обязательными минимумами рубрики**. Последняя
проверка появилась не зря: `demo-sysdesign` полгода стоял с `passed: true` при
`c5 = 0.5` и `min_score_for_pass: 1` — сумма сходилась, и глазами это не
ловилось.

Разбор доступен там, где есть рубрика. `DEMO_BY_COURSE` и `DEMO_BY_RUBRIC`
больше не пишутся руками — выводятся из списка `DEMO_RUNS`. У программ без
рубрики ячейка ведомости не ссылка: показывать разбор работы по Tech QA против
рубрики по Go хуже, чем не показывать ничего.

То же правило действует и на экране проверки: **`demoRunForRubric` возвращает
`null`**, а не подставляет чужой прогон. Пока рубрик было три и прогонов три,
подмена не срабатывала ни разу; после расширения каталога записанный разбор
есть у пяти рубрик из тринадцати, и молчаливый откат на прогон по Go
показывал бы правдоподобное и неверное. Кнопку «Открыть демо-прогон» заменяет
строка о том, что разбора по этой рубрике нет.

## Грабли: что диктует бэкенд

Правила, которые ломаются молча, если о них не знать:

- **название, максимум, вес и проверочные пункты критерия лежат в рубрике** —
  вердикт знает только `criterion_id`. Панель соединяет их сама;
- **`line_numbers`, а не `first_line + index`.** У фрагмента из диффа номера
  строк идут с пропусками (1–4, затем 119–122). Нумерация по позиции уводит
  цитату на чужую строку — на `partial`-файлах это выглядит правдоподобно и
  потому особенно опасно;
- **`partial`** значит, что модель видела не весь файл, и вывод «этого в работе
  нет» здесь ненадёжен;
- **Format Gate возвращает разбор проверок**, и у проверки есть третье
  состояние — `inconclusive`: ответить по доступным данным нельзя. Это не
  провал;
- при `gate.status === 'blocked'` **модель не запускалась**, и черновик надо
  читать иначе;
- **недоступный сигнал детектора — не ноль, а «не смотрели»**;
- **детектор приезжает внутри `ReviewResponse`,** а не отдельным вызовом:
  `with_detection: true` в запросе, `detection` в ответе, один ingest на оба
  разбора. Обратно на `POST /detect` разводить нельзя — это возвращает двойной
  расход лимита GitHub и расхождение ревизий между спанами и цитатами;
- **у отчёта детектора три состояния, а не два.** `detection === null` значит
  «не просили». Отчёт с пустым `signals` — это `DetectionReport.unavailable`:
  детектор не запускался (гейт заблокировал работу) или упал, и сервер прислал
  причину в `limitations`. Показывать в этом случае шкалу нельзя: `overall_score`
  там нулевой по умолчанию, и `0.00` прочиталось бы как «признаков нет».
  Отработавший отчёт всегда несёт сигналы;
- **итог считает агрегатор**: веса, шаг шкалы, обязательные минимумы и штраф за
  просрочку, причём два последних могут обнулить работу целиком. Правка балла
  куратором показывает сумму как предварительную и не выносит вердикт о зачёте —
  пока нет `PATCH /review`, считать это на фронте значит показать правдоподобное,
  но неверное число рядом с объяснением сервера.

Типы генерируются из OpenAPI (`npm run gen:api`), руками `backend.d.ts` не
правят. Так и обнаружилось появление `student_name` в API.

## Как добавить

**Программу в каталог** — запись в `PROGRAMS` (`src/mocks/programs.ts`), затем
`npm run roster`, чтобы пересобрать ведомость. Дашборд, потоки и студенты
соберутся сами. Чего в условии нет — оставлять `null`, а не заполнять
правдоподобным: `passThreshold`, `deadline`, `graceDays` именно для этого
допускают `null`.

**Рубрику** — из интерфейса: «Новая рубрика» на `/rubrics`, дальше либо условие
задания в компилятор, либо чистый лист. Подтверждение кладёт JSON в
`backend/rubrics/` через `POST /rubrics`. Руками положить файл туда же по-прежнему
можно — каталог подхватит его без правок фронта. Шкала, критерии и Format Gate
берутся из условия задания; сумма максимумов критериев с весами должна
дотягивать до `scale.total_max`.

**Записанный прогон** — файл рядом с `src/mocks/demoBackend.ts`: снимок рубрики в
`src/mocks/rubric.ts`, файлы работы, черновик и отчёт детектора в формате
ответов бэкенда. Дальше — запись в `DEMO_RUNS` (`src/lib/runs.ts`); карты
`DEMO_BY_COURSE` и `DEMO_BY_RUBRIC` соберутся из неё сами. Цитаты не
проставляют руками — их ищет `locator()` по тексту файла, как это делает
настоящий валидатор. Перед коммитом прогнать
`scripts/check-demo-runs.ts`: он ловит всё, что иначе ловится глазами и
обычно не ловится.

## Что не сделано

Список честный, по убыванию пользы.

1. **Нет `PATCH /review`.** Правки балла живут в памяти вкладки и не сохраняются;
   итог после правки показывается предварительным. Появится ручка — уйдёт
   оговорка и вернётся вердикт о зачёте.
2. **Чат с моделью выключен.** Ручки нет; на живом прогоне панель об этом
   говорит, на записанных показывает заранее написанную ветку. Показывать
   придуманный ответ рядом с настоящим черновиком нельзя.
3. **Прогон живёт в памяти вкладки.** У бэкенда нет хранилища сдач, поэтому после
   перезагрузки проверку нужно запускать заново. Появятся `submissions` —
   `lib/runs.ts` меняется на запросы.
4. **Нет браузерных тестов.** Логика закрыта юнит-тестами (`npm test`), но
   обход маршрутов на ошибки в консоли и горизонтальный скролл, переход по
   цитате и правка балла до сих пор проверяются руками. Это стоит закрепить в
   Playwright.
5. **Терминология расходится с заказчиком.** В материалах организаторов роли —
   **методист**, **преподаватель**, **ревьюер**; слова «куратор» там нет. В
   интерфейсе везде «куратор» по формулировке задачи. Перед показом жюри стоит
   решить, чей словарь.

## Редактор рубрик

`/rubrics/new` и `/rubrics/:id/edit` ведут в один компонент `RubricEditor`.
Разница только в источнике: у первого это черновик компилятора либо пустая
заготовка, у второго — `GET /rubrics/{id}`.

Что здесь важно и легко сломать:

- **ручка записи одна — `POST /rubrics`, и она принимает рубрику целиком.**
  «Сохранить правку» значит отправить весь объект заново, поэтому редактор
  никогда не открывается на недогруженных данных: то, чего не видно на экране,
  ушло бы на сервер пустым;
- **перезапись требует явного `overwrite`.** По старой версии уже могли быть
  проверены работы, и подмена задним числом делает их баллы необъяснимыми —
  диалог говорит это словами, а не прячет за галочкой;
- **смена `assignment_id` в правке создаёт вторую рубрику**, а не переименовывает
  первую: файл называется идентификатором. Диалог предупреждает; удалять из
  каталога через UI нельзя, ручки нет;
- **`lib/rubric.ts` повторяет `validate_rubric` с сервера дословно**, вместе с
  формулировками. Это исключение из правила «не считать на фронте то, что
  считает сервер»: список поломок нужен во время правки, а не после отказа.
  Правила разъезжаются молча — **при правке `backend/src/avito_reviewer/ai/rubric.py`
  проверьте зеркало**. Источник правды остаётся серверный: его 422 показывается
  как есть;
- **замечания (`rubricAdvisories`) держатся отдельно от поломок** и не блокируют
  отправку. Рубрика без названия сервером принимается, но в каталоге выглядит
  пустой кнопкой — это вопрос вкуса, а не арифметики, и решает его методист;
- **виды проверок Format Gate, которых гейт не исполняет** (`font`,
  `revision_history_visible`, любой свой `check`), помечены в редакторе: они не
  пропадают, а уходят ревьюеру как `inconclusive`. Знать это надо до того, как
  проверка легла в рубрику, а не после первой сдачи;
- **ключи списков — не идентификаторы критериев.** `id` правится прямо в поле, и
  на ключе-идентификаторе карточка пересоздавалась бы на каждом нажатии, теряя
  фокус. Поэтому рядом живёт массив сгенерированных ключей.

Черновик компилятора несёт `warnings`, `open_questions` и `sources`. Первые два
стоят перед критериями и не сворачиваются, цитата из условия — вплотную к своему
критерию: подтверждение без видимого источника это кнопка «ок», а не решение.

## Тесты

```bash
npm test           # один прогон
npm run test:watch # в режиме наблюдения
```

Покрыто не всё подряд, а то, что ломается молча и выглядит при этом
правдоподобно.

`src/lib/rubric.test.ts` — зеркало серверных проверок рубрики. Отдельным
случаем прогоняет **все настоящие рубрики из `backend/rubrics/`**: сервер их
принял, и если зеркало находит в них поломку — сломано зеркало.

`src/lib/rubric.mirror.test.ts` — сторож против расхождения. Читает
`backend/src/avito_reviewer/ai/rubric.py`, считает число правил, вытаскивает
формулировки поломок и проверяет, что все они дословно есть в `lib/rubric.ts`;
заодно сверяет `ID_PATTERN`. Смысла он не проверяет — он ловит движение:
поменяли правило на сервере, забыли здесь — тест падает и заставляет прочитать
оба файла.

`src/lib/workspace.test.ts` — правила адаптера: номера строк из диффа
(`line_numbers`, а не позиция), отметка «в файле есть что показать» (несошедшаяся
цитата находкой не считается), детектор внутри ответа ревью, и запрет на
пересчёт итога после правки балла.

Это не то же самое, что `scripts/check-demo-runs.ts`: тот проверяет
**записанные прогоны** — что фикстуры не разъехались с рубриками; тесты
проверяют **логику**, которая эти прогоны читает.

Тесты лежат рядом с кодом и попадают в `tsc -b`, поэтому выдуманное значение
enum ловится компилятором раньше, чем прогоном.

## Визуальный язык

Метафора — не терминал, а разметка на полях: куратор читает работу и оставляет
пометки. Бумага `#fbfbfa` на поле `#f1f2f0`, графитовый текст, единственный
интерактивный цвет — чернильно-синий, подсветка цитаты — песочная полоса с
линейкой слева. Моноширинный шрифт только там, где действительно код или путь.

Одно громкое место на экран: в Review Workspace это итоговый балл, и кнопка
утверждения стоит рядом с числом, которое утверждает; в редакторе рубрик — то,
что рубрика вообще считается: набранное по критериям против шкалы, и кнопка
подтверждения рядом. Токены —
`src/styles/index.css`, палитра графиков проверена на различимость при
дальтонизме.
